## 4. Findings

### V27C-01 — P1 — Entity deletion fails when an associated device was revoked

**Component:** Repository entity deletion / device lifecycle
**Evidence:** [sqlite.go](./backend/internal/repository/sqlite.go:519) selects only devices with `status='active'` for detachment. The subsequent entity delete occurs at line 549. Migration 007 gives every device an `ON DELETE RESTRICT` entity reference. A revoked device retains its `entity_id` because the revoke operation changes status and revokes its credential but does not detach the device.

**Reproduction:** In an isolated in-memory SQLite fixture with the migration's restrictive FK, insert an entity and an associated `status='revoked'` device, then delete the entity. SQLite rejects the delete with `FOREIGN KEY constraint failed`. The repository selection predicate excludes that device, so its ID is not cleared before the delete.

**Expected:** Entity deletion revokes and detaches every associated device while preserving its tombstone and observations.
**Actual:** Deletion fails atomically when any associated device is already revoked (and can similarly fail for any other non-active status retaining the association).
**Impact:** Core entity deletion is blocked after a normal device revocation workflow.
**Recommended remediation:** Select all devices associated with the entity regardless of status; revoke any remaining active credential, detach each associated device, and audit the transition transactionally. Add repository/API regression coverage for active, revoked, and already-detached devices. No remediation was made in V2.7C.

### V27C-02 — P2 — New backups declare schema version 6 after migration 007

**Component:** Backup creation and manifest verification
**Evidence:** [backup.go](./backend/internal/backup/backup.go:84) constructs every newly created manifest with `SchemaVersion: 6`, although V2.7 databases have migration ledger version 7. `Verify` validates the backup file's internal ledger, but does not compare that ledger version to `Manifest.SchemaVersion`; `readManifest` only accepts either 6 or 7.

**Expected:** A schema-7 backup declares version 7, and verification rejects a manifest whose version differs from the verified database ledger.
**Actual:** A schema-7 backup is labeled version 6, and a mismatched label is not detected.
**Impact:** Backup inventory and schema compatibility metadata are unreliable; operators cannot use the manifest's schema version as evidence of the contained database version. No data loss was reproduced.
**Recommended remediation:** Derive the created manifest version from the live migration ledger and compare manifest and database versions during verification. Add schema-6/schema-7 mismatch tests. No remediation was made in V2.7C.

### V27C-03 — P2 — The sensor-filtered query-plan test does not match the production filter query

**Component:** History query index verification
**Evidence:** Production history SQL in [monitoring.go](./backend/internal/handler/monitoring.go:345) uses `(?='' OR sensor_id=?)`; the test in [service_test.go](./backend/internal/monitoring/service_test.go:273) uses direct `sensor_id=?`. An isolated SQLite `EXPLAIN QUERY PLAN` using the production predicate selected `idx_sensor_observations_entity_time`; the simplified equality query selected `idx_sensor_observations_entity_sensor_time`.

**Expected:** The test verifies the actual production query plan for sensor-filtered, cursor-paginated history.
**Actual:** It verifies a different, more index-selective SQL predicate.
**Impact:** The test does not establish that the production sensor-filtered query uses the documented composite index. The chosen entity/time index still bounds by entity/time, but may scan more rows for a selective sensor filter.
**Recommended remediation:** Run `EXPLAIN QUERY PLAN` against the exact production query/predicate variants and either simplify the SQL predicate to preserve index selection or document measured behavior. No remediation was made in V2.7C.

## 5. Source review summary

### Credentials and CLI

Source review confirms `crypto/rand` 32-byte secrets, SHA-256 hash storage, constant-time comparison, strict token shape and decoded length, one-time CLI output, and no credential/hash fields in device list result structs. Lifecycle changes use transactions and audit inserts; API auth checks the presented credential again inside the write transaction. Device CLI acquires the exclusive shared-maintenance lock, which conflicts with the API's held shared lock. I found no token logging path in the reviewed implementation.

No direct subprocess CLI lifecycle test, concurrent lifecycle test, or explicit audit-failure rollback test was found. The package build and lifecycle service tests pass; these cases remain incompletely verified.

### Authentication, ingestion, and idempotency

Source and composed-router tests support exact-route device authentication, admin middleware on other paths, device-token denial on admin APIs, admin-cookie denial on device ingestion, and unknown API default-deny. Existing auth regression tests exercise sessions, CSRF, Origin, logout, and expiry. The exact credential ID, entity association, device state, and entity state are rechecked inside ingestion transaction. The unique key is database-enforced; concurrent identical retries are tested.

Not independently covered by the current tests: concurrent same-key/different-payload calls, injected transaction rollback after sensor registration, stale/revoked credential race, all timestamp boundaries, oversized-body boundary variants, nested metadata adversarial cases, and retry behavior after the 90-day ingestion age boundary. Device authentication is not an administrator authorization path.

### History APIs and authorization

Source review confirms admin middleware protects monitoring and history APIs; result rows omit hashes and bearer credentials; page limits and history time windows are bounded; history cursor fields are checked against entity/time/sensor filters; latest selects one observation per entity/sensor; cursor continuation is tested for a two-page history sample. The endpoint does not expose deleted entity metadata, while observation snapshots can remain queryable by deleted entity ID.

The latest endpoint ignores `from`/`to` query values rather than applying them. This was not used by the documented latest contract and was not classified as a finding. Page/filter combinations, deleted-entity API results, invalid cursor variants, and latest pagination were not exhaustively tested.

### API lock and rate limiting

Source review confirms an exclusive nonblocking `<db>.api.lock` held for API lifetime and the existing shared `<db>.lock` retained. The source-IP selection honors `X-Real-IP` only for configured trusted proxy CIDRs; tests cover spoofed versus trusted peers. Limiter tests check threshold and bucket cap. No two-process startup/shutdown integration test was found or run, so lock acquisition/release behavior was reviewed at source level only. No multi-process/multi-host rate-limit guarantee is claimed.

### Backup and restore

Temporary schema-6 restore, integrity/FK verification, restore rollback behavior, and existing snapshot tests pass. New backup manifest versioning is defective as V27C-02 describes. No independently passing assertion checks that a new schema-7 backup manifest says 7; manifest mismatch rejection is also untested. Restore interruption was not separately simulated in this phase.

### Frontend

Frontend source and tests cover API filter serialization, an empty render state, and freshness helper thresholds. Automated frontend tests and build pass. No browser executable, Playwright/Puppeteer package, or browser automation tool was available in this environment; therefore no browser interaction, screenshot, responsive viewport, session-expiry UI, map, entity, or geofence browser QA was performed. Component tests were not treated as a substitute for browser QA.
