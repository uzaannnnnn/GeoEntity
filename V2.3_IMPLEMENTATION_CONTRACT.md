# GeoEntity V2.3 — Advanced Entity Management Implementation Contract

**Phase:** V2.3A technical preparation
**Baseline:** V2.2 Map Intelligence, commit `4fa914d958b5c48e6000da1941ce55897a9a57c3`
**Status:** Proposed contract; implementation requires explicit authorization.

## 1. Scope and compatibility

V2.3 adds typed custom attributes, tags, categories, an entity activity timeline, and richer entity details. Keep the React 19/TypeScript/Vite, Go `net/http`, `database/sql`, SQLite, Leaflet, and React Leaflet stack. Keep the existing Go monolith and V1 entity routes, response envelopes, fields, status codes, and validation behavior compatible. No auth, imports, entity pagination/search, geofencing, telemetry, PostGIS, services, or broad redesign is in scope.

The current API has a strict JSON decoder (`DisallowUnknownFields`); do not make the frontend send extension fields until the backend supports them. V1 clients that omit all new metadata continue to create/update entities as they do today. Unknown JSON fields remain rejected.

## 2. Existing architecture and extension points

The current system has:

- **Backend:** `backend/internal/entity/entity.go` owns the V1 entity DTO and validation; `handler/api.go` owns health and CRUD HTTP handlers, strict bounded JSON decoding and error envelopes; `repository/sqlite.go` owns SQLite persistence and the embedded ordered migration runner. The migration ledger records version, name, and SHA-256 checksum. `001_create_entities.sql` is the V1 schema. SQLite is configured for one open connection and foreign keys are enabled.
- **Frontend:** `App.tsx` owns entity loading, selection, CRUD modes and reconciliation; `EntityForm.tsx` handles base entity inputs; `EntityDetail.tsx` renders selected entity information and actions; `MapView.tsx` and its V2.2 components own map interactions. `src/types/entity.ts` and `src/api/entities.ts` represent the current V1 wire contract; the API helper constructs the explicit V1 payload. `utils/validation.ts` validates current base fields.
- **Tests:** Go handler/repository tests use temporary SQLite databases and cover CRUD/migrations. Vitest covers API helpers, validation, state utilities and map behavior (65 tests at V2.2 closure). No browser executable/E2E harness was available at V2.2 closure, so browser rendering and real interactions remain unverified.
- **Dependencies:** frontend uses React 19, TypeScript, Vite, Leaflet/React Leaflet 5 and the V2.2 clustering package. Backend uses the existing Go modules, including `modernc.org/sqlite`; no schema migration framework is needed.

Extend at these seams: add domain types and validation alongside `entity`; add repository transaction operations and additive embedded SQL migration(s); add handlers/routes without changing existing route semantics; add separate typed API clients and metadata view models in the frontend; extend `EntityDetail` and its detail-specific components while retaining `App` as current entity selection owner. Preserve all map state and V2.2 behavior.

## 3. Data model decision

Use normalized relational tables rather than an opaque JSON blob. Definitions and values need server-side type/required validation and a path to indexed filtering in V2.4. SQLite JSON functionality is not required. Use parameterized SQL and explicit application validation.

One additive migration, `002_advanced_entity_management.sql`, is the preferred initial migration. It should create:

1. `attribute_definitions`: stable UUID `id`; `entity_type` constrained to the existing four types; normalized `key`; `label`; `value_type` (`string`, `number`, `boolean`); `required`; optional `min_number`, `max_number`, `max_length`; `archived`; UTC `created_at`/`updated_at`. Unique `(entity_type,key)`. No arbitrary expressions, nested values, defaults, or user-defined validators.
2. `entity_attribute_values`: `entity_id`, `definition_id`, one typed value column each for text/real/integer boolean, and a CHECK requiring exactly one value column consistent with definition type (enforce type consistency in application transaction as SQLite cannot conveniently enforce a cross-table type constraint). Unique `(entity_id,definition_id)`. Entity deletion cascades current values; definition deletion is restricted. Archive definitions in normal operation.
3. `tags` and `entity_tags`: UUID and display name plus normalized name; unique normalized name; unique entity/tag pair. Entity deletion cascades assignment rows.
4. `categories` and `entity_categories`: independently curated flat taxonomy, with UUID, display/normalized names and unique entity/category pair. Entity deletion cascades assignment rows. Categories are many-to-many, as an asset can belong to more than one operational grouping.
5. `activity_events`: event UUID, `entity_id` stored as text **without an entity foreign key**, event type, UTC timestamp, actor kind, nullable actor ID, payload version, and bounded JSON payload. Add `(entity_id, occurred_at DESC, id DESC)` index.

Add indexes for each relation's reverse lookup and for attribute definition lookup. Keep existing `entities` rows, IDs, checks, timestamps and indexes unchanged. Keep foreign keys enabled. Catalog deletion must be restricted while assigned; do not use implicit cascade for taxonomy catalogs.

### Custom attribute semantics

- Definitions belong to one existing `entity.type`, not globally.
- Keys are lowercase ASCII snake case matching `[a-z][a-z0-9_]{0,63}`. Reserve all existing entity field names (`id`, `name`, `type`, `description`, `status`, `latitude`, `longitude`, `created_at`, `updated_at`) and metadata/API names (`tags`, `categories`, `attributes`).
- Initial types: string, finite number, boolean. String max defaults to 2,048 UTF-8 bytes unless a smaller definition bound is set. Definition keys/labels/limits are bounded; max 50 active definitions per entity type and 32 KiB total encoded attribute values per entity request. Existing global request body limit remains in force.
- No default values. An omitted optional field is unset. A V2-aware full replacement enforces required active fields for the entity's current type; values with wrong types, unknown/archived keys, non-finite numbers, or out-of-range values fail validation before writes.
- Once a definition has values, its key and value type are immutable. Label and bounds may change only if all existing values remain valid. Archive definitions rather than deleting used definitions; archived values remain retained and read-only.
- Changing entity type does not delete old-type values. Preserve them and expose them as “previous type / not applicable”; new edits validate against the current type's definitions. V1 clients can still change type while omitting metadata without losing values. Required custom fields are enforced when a V2 client submits attributes; omission by a V1 client is allowed for backward compatibility.

### Tags and categories semantics

- Tags are flexible, cross-cutting labels; categories are a separate, curated, flat operational taxonomy. Neither replaces `type` or `status`.
- Trim and collapse surrounding/repeated whitespace; compare normalized names case-insensitively using Go standard-library lowercase. Preserve a clean display spelling. Full Unicode canonical normalization is out of scope without an approved dependency.
- Unique normalized catalog name; duplicate catalog creation is a conflict (409). Repeated IDs in an entity assignment request are deduplicated as a set. Maximum 50 tags and 20 categories per entity; name limits: 64 characters for tags and 100 for categories.
- Entity assignments use complete replacement semantics. Deleting an assigned tag/category returns 409; caller must first unassign/reassign. No category hierarchy or implicit reassignment in V2.3.

## 4. Activity and atomicity

Activity is append-only through application APIs. Use event kinds `entity.created`, `entity.updated`, `entity.deleted`, `entity.attributes.updated`, `entity.tags.updated`, and `entity.categories.updated`. Store UTC RFC3339Nano-compatible timestamps. Until authentication exists, write `actor_kind: "system"`, `actor_id: null`; never imply an authenticated human actor.

Payloads are versioned and contain a bounded change summary (field/key and before/after values); entity deletion includes a bounded snapshot of base fields, attributes and assignment display names so history survives deletion. Cap long descriptions and custom string values in the event summary with explicit truncation markers, while keeping persisted values and V1 API responses intact. Avoid secrets. Activity can expose sensitive descriptions/custom values; this local/trusted-use risk must be documented. No retention/pruning is included in V2.3; database growth is a known limitation.

Every successful entity create/update/delete and metadata assignment/value change writes its event in the same SQL transaction as the corresponding data mutation. If validation, persistence, or event insertion fails, roll back both. Catalog creation/deletion is transactional; it need not create entity activity. Do not emit events for unchanged attribute or tag/category replacement. Entity update retains the existing `updated_at` contract; record only actual changed fields in the event. Keep activity after entity deletion by omitting the event-to-entity FK. Normal APIs expose no event update/delete operation; consider SQLite triggers preventing direct mutation if they do not complicate migration/testing.

For deletion, read the entity and all metadata inside the transaction, insert `entity.deleted` with its snapshot, then delete the entity (current values/assignments cascade). Activity remains queryable by syntactically valid entity UUID even when that entity no longer exists.

## 5. Proposed API contract

All successful payloads retain the existing `{ "data": ... }` envelope. Existing `/api/health`, `/api/entities`, `/api/entities/{id}` semantics are unchanged. New handlers use strict JSON decoding, bounded bodies, stable existing error envelope, validation before transaction, parameterized SQL, and consistent 400/404/409/413 responses.

| Method and path | Request | Success |
|---|---|---|
| `GET /api/attribute-definitions?entity_type=vehicle` | Query is required and restricted to supported type | `200 {"data":[definition...]}` |
| `POST /api/attribute-definitions` | `{entity_type,key,label,value_type,required,min_number?,max_number?,max_length?}` | `201 {"data":definition}` |
| `PUT /api/attribute-definitions/{id}` | Complete mutable-field object `{label,required,min_number?,max_number?,max_length?,archived}`; immutable entity type/key/value type are read from the stored definition | `200 {"data":definition}` |
| `GET /api/entities/{id}/attributes` | UUID path | `200 {"data":{"entity_type":"vehicle","values":{...},"previous_type_values":{...}}}` |
| `PUT /api/entities/{id}/attributes` | `{ "values": {"license_plate":"B1234","production_year":2024} }`; full replacement of current type values | `200 {"data":{"values":{...}}}` |
| `GET /api/tags` / `GET /api/categories` | None | `200 {"data":[{id,name}...]}` |
| `POST /api/tags` / `POST /api/categories` | `{ "name":"Fleet" }` | `201 {"data":{"id":"…","name":"Fleet"}}` |
| `DELETE /api/tags/{id}` / `DELETE /api/categories/{id}` | UUID path; only unused items | `204`; `409` if assigned |
| `GET /api/entities/{id}/tags` / `/categories` | UUID path | `200 {"data":[{id,name}...]}` |
| `PUT /api/entities/{id}/tags` / `/categories` | `{ "tag_ids":["…"] }` or `{ "category_ids":["…"] }`, complete replacement | `200 {"data":[{id,name}...]}` |
| `GET /api/entities/{id}/activity?limit=&cursor=` | limit defaults 20, max 100; opaque stable cursor | `200 {"data":[event...],"meta":{"next_cursor":"…"}}` |

Activity is newest-first, ordered by `(occurred_at DESC,id DESC)` with keyset cursor pagination; do not use offset. Store timestamps in fixed-width UTC nanosecond RFC3339 form so SQLite text ordering remains chronological. Cursor encoding/decoding is opaque to clients and invalid cursors return 400. Activity reads work for deleted entities. For live entities, return 404 for invalid/missing entity on metadata reads/writes. Event DTO: `{id,entity_id,event_type,occurred_at,actor:{kind,id},payload_version,changes}`; `changes` contains before/after data or a deletion snapshot.

To preserve compatibility, entity POST/PUT remain the original strict V1 DTO and do not accept metadata fields. Metadata is written only through the dedicated subresource endpoints above. A V1 update that omits metadata therefore leaves all metadata untouched. Existing entity response DTO remains unchanged in V2.3; clients fetch metadata subresources.

Suggested error mapping: malformed/invalid value 400 `VALIDATION_ERROR`; missing entity or definition 404; normalized duplicate, assigned catalog deletion, unsupported definition mutation or type conflict 409; request-body or activity-snapshot limit 413. Preserve the current error envelope and do not expose SQLite details. Multi-field validation may use a stable `details` list while retaining the top-level code/message.

Transaction boundaries: entity base mutation + any explicitly supplied metadata + event in one transaction; each metadata replacement + diff + event in one transaction; catalog create/delete in its own transaction; reads are read-only. Frontend implementation starts only after the backend contract is frozen and tests pass.

## 6. Frontend design

Keep current application shell, map, list and selection ownership. Enrich `EntityDetail` with focused sections/tabs:

- **Overview:** existing name/type/status/description/coordinates and actions.
- **Attributes:** definitions loaded for selected entity type; typed inputs and required/bounds hints; distinguish current-type values from preserved previous-type values. Provide a small definition management path for this single-user app (create/edit/archive definitions) without adding roles or a general admin redesign.
- **Tags & Categories:** separate accessible multi-select/editor flows backed by catalogs and complete-replacement APIs.
- **Activity:** newest-first timeline with action label, localized timestamp, “System” actor until authentication, and readable field changes; include load/error/empty and load-more states.

Put typed request/response models and calls in dedicated frontend management API modules rather than overloading `entities.ts`. Keep authoritative validation in Go; mirror limits for prompt UX. Refresh selected metadata after successful writes; retain selection and map marker state. Do not add mock data, local persistence, or frontend-only event generation. Maintain loading, empty, validation, API error, and success feedback. Use native controls where suitable, explicit labels, keyboard access, visible focus, and announce save/error feedback accessibly.

## 7. Migration, preservation, and rollback strategy

Add an additive numbered SQL migration through the existing embedded `MigrateFS` runner and SHA-256 ledger. Do not edit migration 001 or rewrite `entities`. Test from both fresh and populated V2.2 version-1 database fixtures; verify exact entity IDs/values/timestamps survive. Test repeat startup, checksum mismatch refusal, foreign-key behaviors, and transactional rollback on migration failure. Never reset the actual local database. Any test database must be temporary and isolated. Before any future migration of user-owned persistent data, require a verified backup and preservation check; V2.3 tests themselves must not use the persistent database.

Migration rollback is recovery by restoring a verified backup, not destructive down-migration. The migration runner's checksum immutability rule means a released migration is never edited; corrections get a new migration number.

## 8. Acceptance criteria

1. V1 CRUD routes, payloads, JSON envelopes, error behavior and existing entity rows remain operational and compatible; old requests omitting metadata continue to work.
2. Typed definitions are per entity type, bounded and validated server-side; required/unknown/type/bounds/reserved-key/duplicate errors cause no partial writes.
3. Values survive restart; entity type change preserves prior-type values; archived definitions do not erase values.
4. Tags/categories are distinct, normalized, unique catalogs; assignments are idempotent sets with documented complete replacement; assigned catalog deletion is rejected.
5. Every successful requested mutation creates exactly one appropriate activity record in the same transaction; failed writes create none; deleted entities retain readable history.
6. Activity cursor pagination is stable at timestamp ties and limits are bounded; no API can mutate history.
7. Entity details expose Overview, Attributes, Tags & Categories, and Activity with usable loading/error/empty/success feedback and keyboard-accessible controls.
8. V2.2 map, CRUD, marker selection, coordinate updates and map intelligence behavior remain intact.
9. No new dependency, database reset, auth, external service, or unrelated redesign is introduced without a separately documented reason and authorization.

## 9. Required verification plan

**Backend:** Go unit/repository/handler tests; migration tests using temporary fresh and populated V2.2 fixtures; V1 contract regression tests; table-driven attribute validation; tag/category normalization and duplicate semantics; transaction rollback tests including injected event insert failure; delete snapshot/history retention; cursor order/tie/invalid/limit tests; race detector, vet and build.

**Frontend:** Vitest for typed API serialization/error mapping, dynamic definition inputs and type switching, metadata replacement refresh, selector duplicate behavior, timeline loading/empty/error/pagination, and legacy detail behavior; TypeScript production build. Do not claim browser interaction tests without an actual browser harness.

**Integration:** run Go backend against isolated temp SQLite DB and real HTTP client; exercise create/detail/update/type change, attributes, catalogs/assignments, activity, delete/history, validation failures, restart persistence, and old V1 payloads. Verify Vite `/api` proxy and map/entity regression. Do not write to user DB.

## 10. Risks and constraints

- V1 clients can bypass required custom attributes by omitting metadata; retaining that behavior is the compatibility tradeoff until a versioned API is considered.
- Activity payloads may contain personal/operational data and grow without retention. Bound snapshots, avoid secrets, document trusted/local deployment, and revisit retention/access controls before external exposure.
- SQLite's one-connection setting serializes writes. Keep transactions short; do not raise pool size as part of this feature without concurrency evidence.
- SQLite cannot enforce definition/value type across tables with a simple CHECK; repository transaction validation is authoritative.
- Case folding is standard-library lowercase, not full Unicode canonical equivalence.
- Historical values for old entity types need clear, non-editable presentation.
- No authentication or actor identity exists; all events are system-attributed. Restrict the app to trusted/local use until the planned security phase.
- Browser automation remains unavailable at the V2.2 baseline; source/unit tests do not prove visual behavior.

## 11. Sequential implementation phases

1. **V2.3A — Codex planning (this contract):** audit and freeze semantics. No source changes.
2. **V2.3B — Codex backend:** implement additive migration, typed domain/repository transactions, endpoints, validation, event log and Go tests. Start with temporary DB fixtures and V1 contract tests. Report exact DTOs/routes and test results before handoff.
3. **V2.3C — Antigravity frontend:** after reading this contract and V2.3B handoff, implement only frontend types/API/detail flows against the frozen backend. Do not alter backend, schema or API semantics; no mock data or map rewrite. Verify Vitest/build and update handoff.
4. **V2.3D — Codex integration:** verify real HTTP metadata CRUD, atomic event behavior, persistence/restart, V1 compatibility, frontend refresh, Vite proxy and full regression using isolated DBs. Fix narrow integration defects and document browser limitation.
5. **V2.3E — Antigravity independent QA:** read-only source audit and available UI verification; report prioritized, reproducible findings. Do not start automatically.
6. **V2.3F — Codex closure:** only when separately authorized, address findings, run final checks, update docs, inspect Git diff and follow the user's explicit commit policy.

**Antigravity boundary:** V2.3C is frontend-only. Treat endpoint paths, DTOs, dedicated metadata write behavior and validation rules in the completed V2.3B handoff as authoritative. Entity CRUD remains the strict V1 DTO with no embedded metadata fields. If source behavior and this planning contract differ, pause frontend calls that depend on the mismatch and report the exact discrepancy; do not independently change API or invent mock responses.
