## 1. Executive Summary

V2.7 should add a small, authenticated telemetry path for provisioned devices, append-only numeric observations, bounded history queries, and an administrator-only monitoring view. Keep the current Go/SQLite and React architecture. Do not add MQTT, a queue, a charting package, streaming infrastructure, or a new database.

Use a device registry and a separate high-entropy credential table. Bind each device to one entity. The device endpoint accepts one normalized observation per request and derives the entity from the authenticated device; clients cannot choose a different entity. Enforce retry safety with a database uniqueness constraint on `(device_id, idempotency_key)` and compare a canonical payload digest when the key already exists.

Migration 007 is the next sequence number after the verified migrations 001–006. It should add device registry/credential tables, append-only observations, indexes, checks, and triggers. This is a proposal only; V2.7A does not create or execute it.

The supported deployment remains one API process using the local SQLite database. V2.6 rate-limit buckets are process-local, and V2.6's shared maintenance lock does not itself prevent two API processes from running. V2.7B must add an exclusive per-database API instance lock before relying on in-process device/IP/global limits. Multi-process or multi-host ingestion requires a separate shared rate-limit design and is outside this MVP.

### Constraints that affect ingestion

The one-connection SQLite pool serializes database work. A device write, idempotency lookup, device `last_seen_at` update, and observation insert should share one short transaction. Do not perform Argon2id work per device request: device secrets are random high-entropy values and can be verified with SHA-256 plus constant-time comparison. Do not add coordinate writes or geofence evaluation to telemetry ingestion; sensor observations do not change entity location or V2.5 membership/events.

The present V2.6 IP/global limiter is in memory. Two API processes would each enforce only a fraction of a nominal shared limit. V2.7B should acquire a nonblocking exclusive API-instance lock for the database while keeping the existing shared maintenance lock for API/backup coordination. If multi-process operation is later required, replace or augment the process-local limits with a shared transactional limiter and repeat concurrency tests; do not silently claim current limits are global across processes.

## 3. Architecture Overview

```text
Device -- HTTPS + device bearer credential --> exact device ingest route
                                                | validate credential/scope
                                                | idempotency transaction
                                                v
                                     SQLite devices/credentials/observations

Administrator browser -- V2.6 session + CSRF --> existing protected API
                                                | device administration metadata
                                                | monitoring/latest/history
                                                v
                                     React monitoring dashboard
```

Keep the device path, admin path, and health path explicitly classified in one production HTTP composition:

1. `GET /api/health` remains the minimal public liveness response.
2. `POST /api/device/v1/observations` is the only device-authenticated data route. It has a dedicated device credential middleware/handler and never receives an admin principal by implication.
3. All existing APIs, device administration, monitoring, latest, and history routes remain behind the V2.6 administrator session middleware. Unsafe administrator operations retain CSRF and exact Origin/Referer checks.
4. Unknown `/api/*` routes remain default-deny. Tests must assert the route split against the composed production router, including that a device credential cannot access admin endpoints and an admin cookie alone cannot submit telemetry.

No public device registration, anonymous read access, or browser-admin-session authentication on the ingestion route.

## 4. Device Identity and Credential Lifecycle

### Credential format and verification

- Generate a credential ID (UUID) and 32 random secret bytes with `crypto/rand`. Suggested wire form: `gdev_<credential-id>.<base64url-secret>`.
- The ID is a lookup key, not a secret. Store only `SHA-256(secret_bytes)` in `device_credentials`; never persist, log, return again, or include the secret in audit events. Return it exactly once to the operator with `Cache-Control: no-store`.
- Require `Authorization: Bearer ...` over HTTPS. Parse the credential ID and secret strictly, require exactly 32 decoded secret bytes, and use constant-time comparison of fixed-length hashes. Use generic 401 responses for unknown, malformed, wrong, and revoked credentials.
- A high-entropy random secret does not need Argon2id. Do not accept admin cookies, CSRF tokens, passwords, query parameters, or body fields as device credentials.
- Redact the Authorization header and request body in HTTP logs, proxy logs, errors, traces, and metrics. Record credential/device IDs only where operationally needed; never record the bearer value or hash.

### Registry, scope, and lifecycle

Proposed `devices` record: device UUID, nullable entity association, bounded operator label, lifecycle status (`active`, `revoked`, `detached`), optional expected reporting interval, created/updated/last-seen/revoked timestamps. A device has one entity association at a time. Any entity type may be associated; `iot_device` remains a type label, not an authorization rule.

Proposed `device_credentials` record: credential UUID, device UUID, secret hash, created timestamp, last-used timestamp, and nullable revoked timestamp. A partial unique index allows at most one non-revoked credential per device. Rotation revokes the previous row and inserts the new credential in one transaction; old credentials fail immediately. Revocation is also a transaction. Device and credential records are soft-retained for audit/history; do not hard-delete them through the normal workflow.

Use the existing CLI for operator provisioning, listing, rotation, revocation, and detach/reassociation. Credential creation/rotation prints the secret once; terminal output must warn that it cannot be recovered. Never accept a secret as a command-line argument. Device lifecycle operations are infrequent and CLI ownership matches V2.6's provisioning model; require the API stopped and an exclusive maintenance lock for CLI database writes unless V2.7B implements a separately reviewed authenticated online admin operation. Listing never shows a secret or hash.

All provision, rotate, revoke, detach, and reassociation actions write actor-attributed `admin_audit_events` in the same transaction. Audit details include device ID, previous/new entity ID, and action/reason only. Do not audit every observation.

### Entity lifecycle behavior

- Ingestion is allowed only when the device is active, has a non-null entity association, its active credential matches, and the entity exists with status `active`.
- `inactive` and `maintenance` entities reject ingestion with a stable `ENTITY_NOT_ACTIVE` conflict response; the credential remains valid so an administrator can resume the entity without reprovisioning.
- Preserve current entity deletion semantics through an explicit repository transaction: revoke active credentials, mark associated devices detached, set their `entity_id` to NULL, and audit those device changes before deleting the entity. Migration 007 should use `ON DELETE RESTRICT` for registry association so a direct/unreviewed delete cannot silently orphan an active credential. Observation rows store entity/device IDs as immutable snapshots without entity/device cascading FKs, so history remains after entity deletion.
- Reassociation requires an explicit audited CLI operation that revokes existing credentials and issues a new credential for the new entity. Do not silently carry a credential across entity boundaries.

## 5. Telemetry Contract and Validation

### Ingest request

`POST /api/device/v1/observations`

Headers: `Authorization: Bearer <credential>`, `Idempotency-Key: <opaque key>`, and `Content-Type: application/json`.

```json
{
  "sensor_id": "ambient_temperature",
  "value": 21.75,
  "unit": "Cel",
  "observed_at": "2026-11-03T09:15:00Z",
  "metadata": {"quality": "measured"}
}
```

The request represents exactly one measurement. The client does not send `entity_id`, `device_id`, `received_at`, or admin actor data; the server derives those fields. Avoid batches in the first implementation so request size, transaction time, idempotency, and partial failure behavior stay simple.

### Validation decisions

- Strict JSON object; reject unknown fields, multiple JSON values, missing fields, wrong types, and trailing data. Cap the body at 16 KiB before decoding.
- `sensor_id`: lowercase ASCII slug matching `[a-z][a-z0-9_]{0,63}`. Do not accept labels as identifiers.
- `value`: JSON number only. Reject NaN, positive/negative infinity, and values outside a documented finite implementation bound before SQLite binding. Do not accept numeric strings or booleans.
- `unit`: required canonical identifier from a small documented allowlist (initial subset: `Cel`, `%`, `V`, `A`, `m`, `Pa`, `ppm`, `dBm`, `1`). No implicit conversions. API and UI preserve the exact unit. A sensor ID has one immutable unit per device, enforced by `device_sensors(device_id,sensor_id)`; the first accepted observation registers it in the same transaction. A later different unit returns `SENSOR_UNIT_CONFLICT`; use a new sensor ID to change units. Do not aggregate different units into one series.
- `observed_at`: required RFC 3339 timestamp with explicit timezone; parse and store normalized UTC using the existing RFC3339Nano convention. `ingested_at` is server time. Reject timestamps more than five minutes in the future and older than 90 days at ingestion; accept late observations within that window and sort by observation time. These windows are initial policy values, not workload/capacity claims, and should be constants with tests.
- `metadata`: optional JSON object only, maximum 1 KiB encoded, bounded nesting/field count, no credential-like fields. Omit it if not needed; do not allow arbitrary unbounded device payloads.
- Do not accept coordinates, entity status, type, actor identity, or arbitrary SQL identifiers through this endpoint.

Stable error envelope should follow the existing `{error:{code,message,field?}}` shape: 400 `INVALID_JSON`/`VALIDATION_ERROR`, generic 401 `DEVICE_NOT_AUTHORIZED` for unknown, malformed, wrong, revoked, or out-of-scope credentials, 409 `ENTITY_NOT_ACTIVE`/`IDEMPOTENCY_CONFLICT`/`SENSOR_UNIT_CONFLICT`, 413 `REQUEST_TOO_LARGE`, 429 `RATE_LIMITED`, and 500 `INTERNAL_ERROR` without internal details. On auth failures do not reveal whether a device ID exists.

First accepted request returns 201:

```json
{"data":{"id":"<observation-uuid>","entity_id":"<bound-entity-uuid>","sensor_id":"ambient_temperature","value":21.75,"unit":"Cel","observed_at":"2026-11-03T09:15:00Z","ingested_at":"2026-11-03T09:15:04Z","duplicate":false}}
```

An exact retry returns 200 with the original observation ID and `duplicate:true`. A reused key with different canonical payload returns 409 and creates no row.

## 6. Idempotency and Transaction Design

- Require an `Idempotency-Key` header of 1–128 ASCII characters; clients should use a UUID or another stable random value and reuse it for retries of the same logical observation.
- Scope the key to `device_id`, not credential ID, so a retry remains safe across credential rotation. Add `UNIQUE(device_id,idempotency_key)` in SQLite; application-only duplicate checks are insufficient.
- After auth and payload validation, build a canonical representation from the bound device/entity IDs, normalized sensor ID, finite numeric value representation, canonical unit, UTC timestamp, and canonicalized metadata. Store its SHA-256 digest on the observation row.
- In one short write transaction, re-check that credential is active and still belongs to the expected active device/entity, look for an existing `(device_id,key)`, then either return its row if hashes match or return conflict if they differ. If absent, insert the observation and update device `last_seen_at` (rate-limit this timestamp write, e.g. once per minute). Let the unique constraint arbitrate concurrent duplicates; on constraint conflict, load the winning row and compare hashes.
- Commit the observation and last-seen update atomically. No audit event per sample. No overwrite path for accepted history.
- If the process loses the response after commit, retry returns the stored observation. If validation or transaction fails before commit, no observation is visible.

## 7. Proposed Migration 007

Add `007_device_telemetry.sql`; preserve migrations 001–006 byte-for-byte and their ledger checksums. Proposed schema (names may be finalized in V2.7B):

1. `devices`: UUID PK; nullable `entity_id REFERENCES entities(id) ON DELETE RESTRICT`; bounded label; status check for active/revoked/detached; optional positive `expected_interval_seconds`; timestamps; `CHECK` that active devices have an entity and no revocation timestamp. Index `(entity_id,status,id)`.
2. `device_credentials`: UUID credential ID PK; `device_id REFERENCES devices(id) ON DELETE RESTRICT`; 64-character lowercase SHA-256 hex secret hash; created/last-used/revoked timestamps. Partial unique index on `device_id WHERE revoked_at IS NULL`; lookup index on active credential IDs if required. Store no bearer secret.
3. `device_sensors`: `(device_id,sensor_id)` primary key, immutable canonical unit and created timestamp; device FK is restrictive. The first accepted observation inserts this row transactionally. A unit change requires a new sensor ID.
4. `sensor_observations`: observation UUID PK; entity ID immutable text snapshot (no entity FK), device ID and credential ID referencing retained registry rows with `ON DELETE RESTRICT`; idempotency key (1–128 chars); sensor ID and canonical unit; finite REAL value; `observed_at` and `ingested_at` UTC text; payload SHA-256; optional bounded metadata JSON. `UNIQUE(device_id,idempotency_key)` prevents duplicate logical observations. No cascading entity FK, so entity deletion cannot erase history.
5. Indexes: `(entity_id,sensor_id,unit,observed_at DESC,id DESC)` for entity history; `(entity_id,observed_at DESC,id DESC)` for time-filtered history and latest; `(device_id,observed_at DESC,id DESC)` for device diagnostics. Keep index count to these demonstrated queries.
6. Checks: status enum, ID/label/key lengths, numeric type and finite bound where SQLite can enforce it, unit/sensor bounds, metadata length, and nonempty timestamps. Application validation remains authoritative for RFC3339 and JSON semantics.
7. Triggers reject UPDATE and DELETE on `sensor_observations` and `device_sensors`. Device/credential lifecycle rows are mutable only through audited rotate/revoke/detach operations; do not add a trigger that makes lifecycle management impossible.

### Deletion, retention, and rollback

Entity deletion runs one repository transaction that snapshots existing entity activity as today, revokes associated credentials, detaches devices and records device audit events, then deletes the entity and records its audit. `ON DELETE RESTRICT` makes an unhandled path fail closed. Sensor rows preserve IDs and measurements, with no cascade. Device registry rows remain tombstones.

Initial sensor-observation policy: retain indefinitely and never prune automatically. Corrections are new observations with new idempotency keys; history is not updated/deleted. Any future deletion/archive requires its own explicit, audited retention design. This avoids inventing a legal retention period but means database and backups grow with ingestion; V2.7C must measure fixture sizes and document this limit.

Rollback after real observations have been accepted is not a destructive down migration. Reverting the application binary while migration 007 is installed is unsupported unless that binary understands the newer ledger. Roll back by restoring a verified pre-007 backup only before accepting telemetry; after writes, retain the migration and roll forward with a compatible fix. V2.7B must update V2.6 backup manifest/schema-version checks and restore verification from 6 to 7, while preserving V2.6 backup compatibility tests. V2.7A must not create/execute migration 007.

## 8. History and Dashboard APIs

All routes in this section require the V2.6 administrator session. Device credentials are rejected. Responses use existing JSON envelopes and bounded cursor metadata.

| Route | Purpose | Bounds / behavior |
|---|---|---|
| `GET /api/admin/devices?limit=&cursor=` | Registry metadata for operator/dashboard status | Default 50, max 100; deterministic `(created_at,id)` keyset; no hashes/secrets |
| `GET /api/monitoring/latest?entity_id=&limit=&cursor=` | Latest row per entity/sensor/unit for monitored entities | Default 50, max 100; stable keyset order; includes entity/device status and last-seen/freshness metadata |
| `GET /api/entities/{id}/sensors/observations?from=&to=&sensor_id=&limit=&cursor=` | Historical observations for an entity | Default 50, max 200; stable `(observed_at DESC,id DESC)` cursor; filters must be valid |

`from` and `to` are RFC3339 UTC-compatible values; require both or neither, require `from < to`, and cap a query window at 31 days. Without a range, default to the most recent 24 hours. `sensor_id` uses the ingestion identifier grammar. Invalid entity UUID/filter/cursor/range returns 400. Query history by the immutable entity-ID snapshot even after entity deletion; response metadata includes `entity_exists:false` for deleted entities. A valid UUID with no observations returns `data:[]` and an empty cursor. The cursor is opaque, versioned, and bound to entity/filter values so changing filters cannot skip or repeat rows. `limit` outside 1–max is rejected.

Latest response example:

```json
{"data":[{"entity_id":"<uuid>","entity_name":"Pump 4","device_id":"<uuid>","device_status":"active","sensor_id":"ambient_temperature","value":21.75,"unit":"Cel","observed_at":"2026-11-03T09:15:00Z","ingested_at":"2026-11-03T09:15:04Z","freshness":"fresh"}],"meta":{"limit":50,"next_cursor":""}}
```

History response uses the same observation fields and `meta.next_cursor`. The dashboard shows monitored entities from latest/device results, then loads history only for the selected entity; do not fan out one request per entity.

Freshness: when `expected_interval_seconds` is configured, mark readings stale after three expected intervals without a successful device report. If no interval is configured, show last-seen age without asserting stale. Revoked/detached devices receive explicit status labels; retain and display their last observation as historical, never as current active data.

## 9. Security, Rate Limits, Audit, and Observability

- Device auth is a separate principal type and secret namespace from the administrator cookie. Device middleware grants only the exact telemetry ingestion capability, not entity CRUD, monitoring history, audit, backup, or provisioning.
- Verify the credential before accepting payload data; bind `device_id` and `entity_id` from the credential/registry, re-check revocation and entity status inside the write transaction, and fail closed if registry or entity state changes.
- Enforce HTTPS for non-loopback device access through the V2.6 trusted proxy model; do not infer scheme/IP from arbitrary forwarded headers. Use only `X-Real-IP` from configured direct proxy CIDRs, as V2.6 does.
- Initial configurable abuse limits for test/implementation policy: 16 KiB body, one observation/request, 60 requests/device/minute, 300 requests/source IP/minute, and 600 requests/global/minute. These are protective starting values to benchmark and tune, not production capacity claims. Apply per-device, per-IP, and global counters before database-heavy work; cap and expire in-process limiter state.
- Enforce a single API process per DB with an exclusive instance lock while process-local limits are in use. A future multi-process plan must use shared quotas (or a designed SQLite transactional rate table) and account for the single-writer bottleneck before deployment.
- Avoid logging Authorization headers, payload metadata, or raw values. Safe counters: accepted/rejected requests by stable reason, 401/409/429 counts, ingestion latency buckets, DB busy/transaction errors, duplicate count, active/revoked device counts, and oldest/latest observed/ingested ages. Do not label metrics with unbounded IDs or credentials.
- Audit admin provisioning, rotation, revoke, detach/reassociate, and relevant entity-driven device revocation. Do not audit ordinary telemetry. Never store secrets in `admin_audit_events`; observation payload metadata must not accept tokens or credential fields.
- No public registration, multi-role access, admin-to-device credential exchange, MQTT, or broad CORS.

## 11. Performance, Storage, and Retention Assumptions

No production ingestion rate or latency target is asserted. V2.7C should benchmark temporary V2.6-derived databases with synthetic datasets (e.g. 10k/100k/1M rows) and report ingest transaction duration, duplicate retry cost, history query latency, DB page/file growth, backup duration/size, and restore duration. These are test sizes, not production capacity guarantees.

Validate `EXPLAIN QUERY PLAN` for entity/sensor/time queries and cursor continuation; confirm expected indexes are used. Test concurrent duplicate requests and concurrent ingest/history reads under the actual one-connection pool and race detector. Do not add a worker or message broker until measurements identify a requirement SQLite cannot meet.

Indefinite append-only retention means every observation contributes to the live DB and V2.6 Online Backup snapshots. Document measured bytes/row and backup growth from generated fixtures. If a required retention period emerges, propose a separate archive/export, verification, audit, and deletion policy before changing append-only triggers.

## 14. Risks and Trade-offs

| Risk | Mitigation / accepted limit |
|---|---|
| Credential leaks through client, proxy, or logs | One-time display, bearer header only, strict redaction, no storage in browser, random 256-bit secret/hash-at-rest |
| Route accidentally inherits or bypasses wrong auth | Exact route allowlist and composed-router negative tests; unknown API paths remain admin-protected |
| Duplicate/concurrent retry creates repeated readings | SQLite unique constraint plus canonical payload hash and transactional conflict handling |
| Entity deletion leaves working credential | Repository transaction revokes/detaches credentials before deletion; restrictive FK fails closed |
| Unit mismatch creates misleading history | `device_sensors` binds one immutable unit to each `(device_id,sensor_id)`; no conversion; changing units requires a new sensor ID |
| Process-local limits differ across processes | Enforce one API process with exclusive DB instance lock; multi-process requires a separately designed shared limiter |
| SQLite writer serialization limits burst ingestion | Keep transactions short, bound request/rate, measure contention and backup impact; no capacity claim |
| Indefinite history increases DB and backup size | Measure generated datasets; no automatic pruning; any retention change needs explicit archival design |
| Late or clock-skewed sensor timestamps | UTC normalization, +5 minute and 90 day policy bounds, distinguish observed vs ingested time |
| Migration 007 breaks V2.6 backup verifier or rollback | Update schema-version checks, test old/new manifests, require pre-007 restore for binary rollback before telemetry writes |
| Dashboard claims stale data without known device cadence | Optional device expected interval; show freshness unknown when it is absent |

## 15. Acceptance Criteria

V2.7B is ready for V2.7C only when:

- Device credentials are independently provisioned, entity-scoped, hashed, rotatable, revocable, one-time displayed, and denied after revoke/entity detach.
- Exactly the device ingestion endpoint accepts device auth; device auth cannot access admin APIs; the whole composed router defaults to the existing admin protection.
- Strictly validated, bounded telemetry is appended atomically with enforced database idempotency; equal retries are safe and conflicting retries are deterministic.
