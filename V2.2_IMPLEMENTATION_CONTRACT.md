# GeoEntity V2.2 — Map Intelligence Implementation Contract

**Status:** Technical preparation (V2.2A). This document authorizes no implementation. Do not change application source or install packages until V2.2B is explicitly authorized.

**Baseline:** V2.1 commit `35961d71cf9c80b932cd6a68c25c69bb79013131`, workspace `./`.

## 1. Scope and invariants

V2.2 adds only map interactions and presentation:

1. Cluster persisted entity markers.
2. Locate the user's position after an explicit action.
3. Fit all valid saved entity coordinates.
4. Show a map legend.
5. Inspect and copy map-center coordinates.
6. Add compact, accessible map controls.

Preserve the current Go/SQLite backend, V1 entity API, entity DTO, CRUD behavior, and existing map tile configuration. No schema migration, endpoint, authentication, geofence, telemetry, PostGIS, or microservice is needed. No additional feature or broad UI redesign belongs in this sprint.

## 2. Current workspace map architecture

### Component and state ownership

- `frontend/src/App.tsx` owns server-backed `entities`, `selectedEntity`, side-panel mode, `isSelectingLocation`, `draftLocation`, initial/manual `shouldFitBounds`, and the `centerRequest` counter. It owns create/update/delete API calls and reconciles successful mutations into entity state.
- `frontend/src/components/MapView.tsx` owns the Leaflet tree and receives entity/selection/draft props from `App`. It creates type-specific inline SVG `L.divIcon`s and status/selection styling. Each persisted entity currently renders as a keyed React Leaflet `<Marker>` with tooltip, popup, and click-to-select event. The draggable draft marker is rendered separately from the `entities.map(...)` block.
- `MapController` uses `useMap()` to fit or pan, fly to a newly selected entity, honor explicit center requests, and pan to a draft coordinate.
- `MapEvents` uses `useMapEvents()` and forwards map clicks only while location selection is active. Existing click coordinates are passed as `(latitude, longitude)`.
- `frontend/src/utils/mapConfig.ts` resolves `VITE_MAP_TILE_URL`, `VITE_MAP_ATTRIBUTION`, and `VITE_MAP_MAX_ZOOM` with OSM defaults. `MapView` passes these to the existing `<TileLayer>`.
- `frontend/src/App.css` defines marker shapes/status styles, picker banner, map and side-panel layout, and responsive behavior. At widths up to 900px the map occupies the upper 52% and the panel is below it. Leaflet's built-in zoom control is currently enabled by default; attribution is supplied to the tile layer.

### Current event and camera behavior

- Entity marker click calls `onSelectEntity(entity)`. The parent selects it and switches to the detail panel.
- Entity-list selection updates the same parent selection; the map then uses `flyToEntity`, currently zoom 13.
- Add/edit form map clicks and draft drag update `draftLocation` in `App`; the draft marker uses a high z-index and is already a distinct layer from persisted entity markers.
- Initial load and manual refresh set `shouldFitBounds`; entity mutations update/upsert/remove by ID and refresh from the V1 list endpoint.
- Current fit logic filters only non-finite latitude/longitude, uses zoom 12 for one point, and `fitBounds` with 50px padding and max zoom 14 for multiple points. It does not check geographic ranges, and no explicit fit action, empty-data response, or all-invalid response exists.

### Existing limitations

- Every entity is rendered as an individual React Leaflet marker; there is no clustering, locate-me action, legend, map-center inspector, or compact map toolbar.
- `App` has no browser-location state. The geolocation API must remain a map-local concern.
- There is no browser E2E/map interaction harness. Existing tests use Vitest and pure utilities; V2.2B must add deterministic tests and document manual browser checks.
- The list API is unpaginated. Clustering reduces visible marker clutter but does not reduce API payload size or the number of React child elements. Do not claim it solves large-dataset/network performance.

## 3. Component and state plan

Keep global entity selection and draft form state in `App`; keep ephemeral map-only state inside `MapView` or small components beneath it.

Proposed responsibilities for V2.2B:

- `MapView`: retain current public props and tile configuration; coordinate map-local control state and compose layers/controls.
- `EntityMarkerLayer`: render only saved `entities`, with stable `key={entity.id}`, current `createEntityDivIcon`, tooltip/popup, selection callback, and cluster group.
- `DraftLocationMarker`: preserve the existing draggable draft marker outside the cluster group.
- `UserLocationLayer`: render a visually distinct, transient fix and optional accuracy radius outside the cluster group.
- `MapController`: keep camera commands centralized; run fit-all, user-location fly-to, and selected-entity reveal/centering.
- `MapToolbar`: compact React buttons in a map overlay for Fit all, Locate me, Legend, and Coordinate inspector. Keep the default Leaflet zoom control.
- `MapLegend`: static visual key derived from the actual entity/status marker styles and the transient map layers.
- Coordinate inspector UI: display the current map center as labeled latitude/longitude and provide a copy action; do not change `selectedEntity`.

Suggested state flow:

```text
App (entities, selectedEntity, draftLocation, location-picking mode)
  └── MapView
      ├── EntityMarkerLayer (persisted entity IDs only; clustered)
      ├── DraftLocationMarker (separate; editable by existing flow)
      ├── UserLocationLayer (MapView memory only; never API/entity state)
      ├── MapController (camera operations and center updates)
      └── MapToolbar → Legend / Coordinate inspector
```

Only existing entity selection and draft-coordinate callbacks cross back into `App`. Locate-me results, legend visibility, coordinate-inspector copy status, and camera-center display remain ephemeral map UI state.

The wrapper README explicitly supports React 19 and React Leaflet 5, documents `chunkedLoading`, and includes a custom cluster icon example. The upstream engine supports cluster-click zoom-to-bounds, `zoomToShowLayer`, spiderfying at max zoom, and removing offscreen markers. Use these as capabilities to verify, not assumptions about every wrapper version. See links in §12.

### Required integration behavior

- Put only persisted entity `<Marker>` children inside `MarkerClusterGroup`. Keep the draft marker, current-user marker/accuracy shape, map controls, and any temporary inspection UI outside it.
- Retain entity `id` as the React key. Keep the existing custom SVG icon on each child marker. Cluster icons should be a compact count bubble, with count equal to persisted child entities; keep the cluster visual distinct from an entity type/status marker.
- Cluster click zooms to the cluster bounds. At maximum zoom, overlapping saved entities remain discoverable (spiderfy or another verified accessible selection path).
- Preserve parent-controlled selected entity and its details. When an entity is selected from the side list while clustered, ensure its marker can be revealed/centered (for example, the group `zoomToShowLayer` API) and retain the selected halo/z-index behavior. A marker click after cluster expansion must still call the existing selection callback.
- Use stable ID keys and the current canonical entity array. Create/update/delete/refresh must not leave stale or duplicate cluster children. Coordinate updates must move the existing logical entity marker; test cluster refresh/update behavior in the chosen wrapper.
- Verify clicking a cluster while location-picking mode is enabled does not accidentally create a draft coordinate through map click propagation.
- Start with documented plugin defaults unless a tested product need requires tuning. Candidate explicit options are `chunkedLoading`, `zoomToBoundsOnClick`, `spiderfyOnMaxZoom`, and `removeOutsideVisibleBounds`; do not enable hover coverage polygons by default because they add visual clutter and are awkward on touch.

### Dependency decision and release gate

No dependency is added in V2.2A. In V2.2B, evaluate and pin a compatible `react-leaflet-cluster` release rather than using a floating latest version. Add its two documented CSS imports. Confirm the actual lockfile peer resolution, MIT license text, `npm test`, `npm run build`, and Vite production bundle delta. If any peer/build failure occurs, stop and report before replacing it with a home-grown adapter.

## 5. Locate Me behavior

- Show a clearly labeled **Locate me** button. Call `navigator.geolocation.getCurrentPosition` only from its click/keyboard activation handler. Never call `watchPosition`, request permission on page load, or proactively query permission.
- If `navigator.geolocation` is absent, show an “Location is unavailable in this browser” status without throwing.
- On success, retain `{latitude, longitude, accuracy}` only in MapView memory, render a distinct current-location dot and optional accuracy circle, and pan/fly to the point at a useful zoom (cap by configured tile max zoom). Do not add it to `entities`, `draftLocation`, the selection, URL, local/session storage, or any API payload.
- Use a one-shot fix with documented options (suggested `maximumAge: 30_000`, `timeout: 10_000`, `enableHighAccuracy: false`; do not request continuous high-accuracy tracking). These are defaults, not product guarantees; keep timeout configurable only if a real requirement appears.
- Map error codes to separate, understandable UI states: `PERMISSION_DENIED`, `POSITION_UNAVAILABLE`, and `TIMEOUT`; include retry via the same explicit button. Do not display raw browser internals.
- While requesting, expose a busy state and prevent duplicate requests. A prior fix may remain displayed during a retry; do not silently replace it until a new success.
- The coordinates must never be sent to the GeoEntity backend or persisted. Normal basemap tile requests after moving the view can reveal the approximate viewed area to the configured tile provider; this is distinct from sending a coordinate to the backend and should be noted in the privacy copy if needed.
- Geolocation requires a secure context (HTTPS or localhost in normal browsers); test localhost and document the deployment requirement.

## 6. Fit All Entities

Use a pure helper to accept only entity points where latitude and longitude are finite and in inclusive ranges `[-90, 90]` and `[-180, 180]`. Do not mutate entity state or send requests.

| Input | Required behavior |
|---|---|
| Zero entities or zero valid points | Disable Fit all when there is no valid point. If all coordinates are rejected, keep the map in place and show a concise status; never pass invalid values to Leaflet. |
| One valid point | Animate to `[latitude, longitude]` at a useful zoom, suggested `min(13, configuredMaxZoom)`. |
| Several valid points | Fit bounds around valid saved points with padding (suggested 40–48px) and a maximum useful zoom (suggested 14, additionally capped by configured max zoom). Use a brief animated transition and avoid abrupt reset of the user's view. |
| Several entities at identical coordinates | Treat the unique spatial extent as a single point for camera selection, while retaining all entity IDs/markers in the cluster layer. |
| Invalid points mixed with valid points | Exclude invalid points and fit only valid points. |

Keep current initial-load/refresh fitting semantics compatible. Consolidate the logic behind a single camera helper so the explicit Fit all button and initial/manual refresh do not drift. Keep existing selected-entity and draft panning behavior; Fit all must not clear selection or draft state.

## 7. Legend contract

Legend labels must be derived from the actual marker implementation and remain visible when expanded:

- **Vehicle / IoT device / Facility / Other:** show the same SVG glyph used by the entity marker (`car`, chip, building, cube). Type is encoded by glyph, not by invented per-type colors.
- **Active / Maintenance / Inactive:** show the existing status border and status dot using `--color-active`, `--color-maintenance`, and `--color-inactive`, with text labels. Color must not be the only cue.
- **Selected entity:** explain the existing blue selection halo as a state indicator, not another type/status.
- **Cluster:** show a count bubble; its number is the number of persisted entity markers represented. Do not imply that the cluster is one entity or that count is a filtered backend total.
- **User location:** show the new distinct blue location dot and, if implemented, its translucent accuracy radius.
- **Draft location:** show the existing dark pin with cyan border/ripple and label it as an unsaved create/edit coordinate.

Place legend content in a small collapsible panel in the map area. Do not cover the OSM attribution or picker instructions. Keep wording aligned with `createEntityDivIcon`, CSS variables, and the final cluster/user-location icon code.

## 8. Coordinate Inspector

- Show the current map center as two explicitly labeled values: `Latitude` and `Longitude`, in that order. Use six decimal places to match `formatCoordinate` and existing entity details.
- Copy as plain text `latitude, longitude` (example: `-6.208800, 106.845600`). Label the button “Copy map center coordinates”; announce success/failure in a small `role=status` message. Do not silently fail when Clipboard API is unavailable; provide selectable text/fallback copy.
- Update from Leaflet `moveend`/camera changes, not on every pointer pixel. The copy action must use the values currently displayed.
- This uses Leaflet `[latitude, longitude]`. Never label or copy it as GeoJSON. GeoJSON order is `[longitude, latitude]` and is out of scope for this inspector.
- Copying/inspecting coordinates must not change selected entity, side-panel mode, draft location, or backend state. Entity selection may move the map center as it does today, after which the inspector reflects that map center.
- Keep the values keyboard selectable and expose labels to assistive technology. Do not announce every animation frame.

## 9. Advanced map controls and accessibility

Keep controls compact and inside the map section. Preserve Leaflet's existing zoom control (top-left) and attribution (bottom-right). Put the new toolbar at the upper-right, away from attribution and the centered location-picker banner. The desktop side panel occupies a separate 410px column; on mobile the map is the upper half, so keep controls compact and test at narrow widths.

Controls:

1. **Fit all** — disabled when there are no valid saved points; never includes user or draft locations.
2. **Locate me** — explicit one-shot geolocation action with requesting/error feedback.
3. **Legend** — toggle with `aria-expanded`/`aria-controls`.
4. **Coordinate inspector** — toggle or persistent compact readout with an explicitly named copy button.

Use native buttons, visible text or accessible names, keyboard focus styles, adequate contrast/target size, and state conveyed by more than color. Active toggles expose `aria-pressed` as appropriate. Keep focus visible and focus order predictable. Prevent map drag/zoom event handling from swallowing toolbar interactions. Do not add a compass, scale, basemap selector, or decorative control in this sprint.

## 10. Testing and acceptance criteria for V2.2B

### Unit/component tests

- Pure valid-coordinate/bounds helpers: empty input, one point, multiple points, mixed invalid/out-of-range points, and duplicate coordinates.
- Cluster child source is exactly saved entities keyed by stable ID; draft and current-user layer never enter the group.
- Create/update/delete/refresh sequence yields no duplicate marker IDs and updates the coordinate of an existing ID.
- Selecting an entity from the list while its marker is clustered reveals the correct marker; selecting an expanded child preserves details/popup behavior.
- Cluster click zooms; dense and sparse data sets behave correctly; overlapping points stay selectable.
- Mock geolocation success, unsupported API, permission denied, unavailable, timeout, retry, busy state, and stale-fix behavior. Assert `entitiesApi` is never called with user coordinates and there is no local/session storage write.
- Fit-all does not call Leaflet with invalid coordinate ranges and does not clear current entity/draft selection.
- Legend labels and icon examples match entity/status/cluster/user/draft styles.
- Coordinate inspector has lat-then-lng six-decimal output, copies exactly that string, updates after camera movement, and preserves selection/draft state; test clipboard rejection/fallback.

### Build and manual/browser checks

- Run `npm test` and `npm run build` after dependency addition and CSS imports.
- Exercise with an isolated backend DB seeded with a deterministic persisted dataset: zero, one, sparse points, a dense city cluster, multiple entities at identical coordinates, and invalid defensive fixtures at the map-helper boundary.
- Verify add/edit location picking remains separate from clusters and inspect mode; update coordinates, refresh, delete, and revisit the same cluster region to check for duplicates/stale markers.
- Verify geolocation is requested only after the button action; verify all error states and that reload removes the transient location.
- Verify visible attribution and all controls at desktop and mobile sizes, including the Vite production build. Keyboard-test zoom, Fit, Locate, legend, copy, and disclosure controls.
- No mock entity source may replace the backend in app runtime. Test fixtures are isolated and deterministic.

### Done criteria

- All six requested map capabilities work together without changing the V1 API or database.
- Saved entity marker IDs, custom icons, selected details, and CRUD synchronization remain intact.
- Draft and user location are visibly distinct and are never clustered or persisted/transmitted to the backend.
- Empty/single/multiple/invalid Fit all cases match §6.
- Legend accurately describes the final marker styles; coordinate inspector is correctly labeled and copies lat/lng.
- Controls are accessible and do not hide attribution or picker instructions.
- Tests and production build pass; bundle change and tested marker-count profile are recorded.

## 11. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Wrapper/engine peer or Vite compatibility differs from metadata | Pin exact candidate version in the implementation PR, inspect resolved peers, add documented CSS, and require clean build/tests before merge. Do not implement a fallback until this is demonstrated. |
| Underlying MarkerCluster has a slow release cadence | Keep it isolated behind `EntityMarkerLayer`; monitor upstream; avoid app-specific patches inside vendor code. |
| React child reconciliation leaves stale cluster layers on marker move/remove | Stable keys and deterministic create/update/delete/refresh component tests; use documented cluster refresh APIs only if tests show a need. |
| Existing fit/selection camera effects race with explicit Fit or Locate | Route camera changes through `MapController` with explicit request/priority semantics; test selection, fit, and locate interactions. |
| Draft map clicks are mistaken for marker/cluster interactions | Keep draft marker outside cluster; verify event propagation with location-picking mode active. |
| User location is sensitive | One-shot explicit opt-in only, in-memory state only, no backend/local storage, visibly transient. Explain that tile requests disclose the viewed region to the tile provider. |
| Large dataset still costs API/React work | Profile 1,000 persisted entities with the current unpaginated list; record initial render and interaction behavior. Clustering is not a substitute for pagination or vector/server-side aggregation, which remain out of scope. |
| Legend drifts from visual CSS | Reuse shared marker/icon definitions or test examples against the same style tokens; avoid duplicated color declarations. |
