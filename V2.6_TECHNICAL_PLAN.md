# GeoEntity V2.6 — Security & Reliability Technical Plan

**Phase:** V2.6A — planning complete
**Baseline:** `master`, `43ce1a7d51950a6cc0ec79692cc3b779b252340b` (`feat: complete GeoEntity V2.5 geospatial intelligence`)
**Parent:** `8486b20207b68bcf5bb115b6aa414630f4094442`
**Authorization:** Planning only. V2.6B implementation is not authorized.

## 1. Executive summary

V2.6 should add one protected administrator, server-side browser sessions, authorization for every existing data route, CSRF/origin checks, bounded throttling, a separate append-only administrator audit trail, and a tested SQLite backup/recovery workflow. It should also measure the V2.5 geofence write path, retain geofence history indefinitely, and correct the documented frontend class/style mismatches. Keep the existing single-process Go/SQLite architecture unless measurements demonstrate a concrete reliability or latency problem.

Use password login with Argon2id and a same-origin, opaque server-side session cookie. Do not add registration, multiple roles, SSO, or public identity integrations. Treat the existing API as private until the security gate is complete. Keep the existing immutable V2.5 event records and V2.3 system-actor activity records unchanged.

## 4. Authentication and session design

### Administrator credential

- Exactly one local administrator row, with a fixed singleton identity. No signup route and no default password. `backend/cmd/admin` (or an equivalent explicit CLI subcommand) provisions the first password and performs offline recovery; read it from a no-echo terminal prompt, never a command argument, log, or committed environment file. Provisioning is atomic and refuses to overwrite an existing admin unless an explicit reset command is used.
- Require at least 15 Unicode code points, permit at least 64, accept spaces and password-manager paste, do not trim/truncate, and do not impose character-class rules. Normalize Unicode consistently to NFC at set and verify time. Reject a versioned blocklist of common, compromised, and GeoEntity/admin-context passwords. Do not require periodic rotation; require a change after suspected compromise. These choices follow current NIST digital identity guidance.
- Hash with Argon2id using a salted, versioned PHC-format verifier; never encrypt or store plaintext. Start benchmarking at the OWASP minimum profile `m=19 MiB, t=2, p=1`, 16-byte random salt and 32-byte output; tune on the target host without going below that floor. Bound concurrent hash work with a semaphore and limit password byte length before hashing to prevent memory/CPU exhaustion. Pin and review `golang.org/x/crypto` only in V2.6B; no dependency is added in V2.6A.
- Return the same generic login failure for unknown/malformed credentials and wrong password. Use a dummy verifier for the nonexistent-user path if provisioning is incomplete. On login, rotate/create a fresh session; never accept a caller-supplied session ID. Password change requires current-password verification, replaces the verifier, revokes all sessions, and issues a new session only after successful reauthentication. Lost-password recovery is an operator-run CLI reset that revokes every session; no email/KBA recovery.

NIST SP 800-63B-4 specifies a 15-character minimum for single-factor passwords, blocklist checks, and throttling; OWASP recommends adaptive password hashing such as Argon2id. See [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html) and the [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).

### Browser sessions

- Generate a 32-byte random bearer secret with `crypto/rand`, encode with base64url, and set it only in an HttpOnly cookie. Store only `SHA-256(secret)` as the session lookup/verifier; compare in constant time. A plain hash is appropriate for a uniformly random high-entropy token; password KDFs are not needed for session secrets.
- Production cookie: `__Host-geoentity_session; Secure; HttpOnly; Path=/; SameSite=Lax`, with no `Domain`. Use a session cookie without browser persistence; enforce expiry on the server. Keep the frontend same-origin and do not put tokens in localStorage, URLs, or logs.
- Store sessions in SQLite with admin ID, token hash, CSRF-token hash, creation time, last activity, idle expiry and absolute expiry. Initial policy: 30-minute idle timeout and 12-hour absolute lifetime, both server enforced; make values configurable only if the deployed threat/usage review needs it. Update `last_seen` at most once per minute to avoid a write for every request; periodically delete expired/revoked session rows in bounded batches.
- Use a per-session 32-byte CSRF token returned in auth JSON and held in frontend memory. Store only its hash and require `X-CSRF-Token` for POST/PUT/PATCH/DELETE. Rotate it with the session. Login has no authenticated session yet, so require exact trusted Origin/Referer, JSON content type, and same-origin Fetch Metadata; do not allow credentialed cross-origin CORS.
- Rotate the session at login and after password change. Logout revokes the server row and expires the cookie. Session revocation and password reset must invalidate copies of a stolen cookie. Do not bind session validity to a mutable user-agent/IP; those are not authenticators.
- Behind TLS termination, set the Secure flag from trusted server configuration, not untrusted `X-Forwarded-Proto`. Do not infer the public origin from arbitrary Host/Forwarded headers. Local Vite use must explicitly allow `http://localhost:5173`; any `GEOENTITY_DEV_COOKIE_INSECURE=true` override must be explicit and refuse non-loopback binds. The production cookie remains `__Host-` and Secure.

Cookie properties, rotation, server-side expiry, and session fixation controls follow the [OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).

## 5. Authorization and API protection

Use a single `admin` principal; do not create a role matrix. In the production HTTP composition, protect every current `/api/*` data route, including entities, query/map, metadata/activity, imports/exports, geofence CRUD, membership, event history, and a bounded `GET /api/admin/audit` read. `GET /api/health` remains public and returns only its current liveness status. Public auth routes are limited to login and the minimal session/CSRF bootstrap/logout contract; session introspection may return only the current admin identity and CSRF token, never password/session material.

All state-changing methods require an authenticated session, CSRF validation, and exact origin validation. Health remains GET-only. Add tests against the composed production handler, not only direct calls to `API`, so future routes cannot bypass the wrapper. Return consistent 401/403/429 envelopes without secrets. Preserve existing V1/V2.4/V2.5 routes, success codes and response envelopes after authentication; only the browser login flow and auth endpoints are new.

Change the default `GEOENTITY_ADDR` to `127.0.0.1:8080`. Add explicit `GEOENTITY_PUBLIC_ORIGIN` and optional `GEOENTITY_TRUSTED_PROXY_CIDRS` settings; trusted proxies must overwrite forwarding headers. An operator may explicitly bind another interface only with TLS termination and network controls. Keep CORS disabled; if a later use case requires CORS, list exact origins and credential policy in a separate security review. Never trust client forwarding headers unless the immediate peer is on the configured proxy allowlist.

## 6. CSRF, origin, and rate limiting

For every unsafe browser request, require the session-bound synchronizer token in `X-CSRF-Token` and a source `Origin` equal to the configured target origin. If Origin is absent, allow only a Referer whose parsed origin exactly matches; reject `Origin: null`, malformed values, suffix matches, and requests with neither signal. Login is protected with the same exact origin policy, Fetch Metadata where available, and JSON-only content type. `SameSite=Lax` is defense in depth, not the only control. Keep GET/HEAD/OPTIONS free of mutation. Do not trust `Host`, `Forwarded`, or `X-Forwarded-*` to determine the target origin.

Rate limits:

- Login: persistent per-account consecutive-failure state with increasing delay capped at 60 seconds, reset on success; do not permanently lock the sole administrator. Add bounded in-process per-source-IP and global buckets before Argon2id, a hard cap on bucket count with expired-entry cleanup, and a maximum one concurrent KDF initially. Unknown account and wrong password paths share timing and messages. The implementation must demonstrate that an attacker cannot grow limiter state without bound.
- Source IP is `RemoteAddr` unless the direct peer matches configured trusted-proxy CIDRs and that proxy overwrites client forwarding headers. Ignore arbitrary `X-Forwarded-For` values.
- Authenticated entity/geofence writes, session/password operations, import, and export receive route-class limits. Keep 1 MiB JSON and 5 MiB/5,000-row import bounds. Derive actual request rates and burst values from a small load baseline and expected single-admin usage; document selected defaults in config and test the Nth/N+1th request and recovery. Do not invent throughput or availability claims.
- The one-process limiter resets on process restart; deployments exposed beyond loopback must also configure an edge proxy limit. The proxy is defense in depth, not the only account throttle.

OWASP recommends synchronizer tokens for stateful sessions and exact source-origin verification; it warns that SameSite alone has limitations. See the [OWASP CSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html). NIST requires effective throttling for password guessing; avoid account lockout that creates an easy permanent denial of service.

## 7. Audit identity

Add `admin_audit_events` in migration 006 as a separate append-only table with event ID, UTC time, `actor_id`, actor label snapshot, action, resource type/ID, request ID, payload version, and bounded redacted details. Keep actor identity snapshot-based and omit foreign keys to the admin row so audit history survives credential resets. Add UPDATE/DELETE rejection triggers. Insert the audit row in the same repository transaction as each successful security-sensitive mutation. Cover entity, metadata/catalog, import commit, geofence definition, password/session administration, and backup/restore operations. Never log passwords, session IDs, CSRF tokens, or full imported records.

Do not rebuild or update V2.3 `activity_events`: its schema only permits `actor_kind='system'`, and those rows are immutable. Preserve historical `system` actors as-is; existing activity response remains backward compatible. Keep V2.5 `geofence_events` coordinate-transition meaning and immutable snapshots unchanged. Admin action audit answers “who requested the write”; geofence event answers “which saved coordinate transition was recorded.” Do not backfill an admin identity onto old records.

## 8. SQLite backup and restore

V2.5 uses `modernc.org/sqlite v1.61.1` and one `database/sql` connection. Its installed driver source exposes SQLite's Online Backup API through `NewBackup` on its raw connection; V2.6B must prove this access path with a temporary-database test before relying on it. Prefer SQLite's online backup API to copying a live `.db` file. It produces a consistent snapshot and avoids assuming anything about rollback-journal/WAL sidecars. See the [SQLite Online Backup API](https://www.sqlite.org/backup.html) and current [`modernc.org/sqlite` package](https://pkg.go.dev/modernc.org/sqlite/v1.61.1).

Proposed operator-only CLI, never an HTTP endpoint:

- `geoentity admin backup create|list|verify` and `geoentity admin restore --from <verified-backup>`; names may follow the existing `cmd/api` layout. Backup destination must be outside the live database path. Set backup directory mode 0700 and files/manifests mode 0600. Include UTC timestamp, app/schema migration versions, file size, and SHA-256 in an atomic manifest. A checksum detects accidental corruption; it is not encryption or a signature.
- Use `GEOENTITY_BACKUP_DIR` and configurable `GEOENTITY_BACKUP_KEEP` (initial default 10). Create the new snapshot to a unique temporary destination, finish/close it, compute checksum, run full `PRAGMA integrity_check` expecting exactly `ok`, run `PRAGMA foreign_key_check` expecting zero rows, verify migration ledger continuity/checksums and selected application invariants, then atomically publish the manifest. Prune older verified backups only after a new backup has passed. Never remove the last known-good backup after a failed run.
- Measure backup duration, size, and request/write blocking under synthetic workloads. The current one-connection pool may queue API work while backup acquires that connection. If online snapshots exceed measured operational tolerance, use a documented maintenance window; never silently copy a live database file.
- Restore is offline: stop the service and verify it is stopped; verify manifest/checksum and integrity in an isolated temporary path using read-only/direct SQLite access that does not run migrations or geofence backfill. Make a separate verified snapshot of the current DB, restore the candidate to a sibling file on the same filesystem, recheck ledger, integrity, foreign keys and application invariants, then perform an atomic swap. Preserve the pre-restore DB for rollback until the operator verifies startup and read/write behavior. If restore fails, keep the old DB in place. Revoke all sessions in the restored candidate before service start, since a point-in-time backup may contain still-valid session hashes.
- Document backup scheduling as an operator-managed timer/cron choice; V2.6 does not add a background scheduler. Store backups with restrictive permissions and include them in tested off-device protection if the operator requires off-device recovery. Do not put them in Git or the public static directory.
- Restore drill uses only disposable generated databases, verifies selected entity/activity/geofence/event counts and sample IDs, starts the application on the restored copy, exercises a harmless read/write, and records elapsed backup/restore time and size. Establish RPO/RTO only after measuring representative data volume; none is asserted here.

SQLite documents the Online Backup API as a consistent snapshot method for active databases. `PRAGMA integrity_check` returns `ok` on success and checks database structure and constraints; `foreign_key_check` is an additional application-level check. See [SQLite backup](https://www.sqlite.org/backup.html) and [SQLite PRAGMA documentation](https://www.sqlite.org/pragma.html).

## 9. Geofence performance

Start from the V2.5 synthetic observation: one entity update evaluating 100 enabled 256-vertex polygons took about 14.38 ms and allocated 5.29 MB/op on the recorded host. This is not representative production capacity. `backend/internal/repository/geofence_memberships.go` synchronously loads enabled definitions and evaluates them in the entity transaction; `sqlite.go` limits the pool to one open connection.

V2.6B should add benchmark fixtures for circle-heavy, mixed, and maximum-vertex polygon sets at several entity/zone counts; report p50/p95 transaction duration, allocation/heap profiles, SQLite time/rows, write queue delay, and concurrency/race behavior. Re-run on the target hardware and label generated data. Separate geometry parse/allocation costs from SQL and transaction overhead. Do not use the persistent database as a fixture.

Keep synchronous evaluation unless measured representative scale misses an agreed interaction/write budget or creates unacceptable queueing. First optimize the measured hot path (e.g., reuse parsed geometry safely by immutable definition version, reduce transient allocations, or avoid repeated scans) and remeasure. Do not introduce a worker/queue, eventual membership state, or new index without evidence and explicit consistency design. Derive any service target after the baseline; do not claim a capacity from the 14.38 ms result.

## 10. Event history retention

Recommendation: retain V2.5 `geofence_events` indefinitely in V2.6. This is a single-admin operational audit/history feature with immutable rows, and there is no stated legal or storage requirement that justifies deleting them. Keep the current append-only triggers and event API semantics. Backups provide recovery; verified export/archive can provide a second copy but does not authorize deleting source events.

Do not add TTL cleanup or weaken/remove triggers. If measured storage growth or a legal retention obligation later requires expiry, define an explicit privileged archival workflow, export format, checksums, verification, operator approval, retention schedule, and separate migration/audit design. Preserve the archived chain of evidence and record what was removed; do not retroactively alter actor/event snapshots. Backup-file retention (`GEOENTITY_BACKUP_KEEP`) is separate from event retention.

## 11. V2.7 compatibility — Essential IoT Monitoring

V2.6 should leave a clean boundary for later device credentials without building telemetry now. V2.7 should use separate high-entropy device/API tokens, show a token only at provisioning, store only a fast hash/verifier, scope each credential to one entity and permitted ingestion action, and support rotation/revocation. Do not reuse administrator passwords, browser session cookies, or admin audit credentials for devices.

V2.7 ingestion should have bounded body/sample/batch sizes, strict units/timestamps, server-side entity scope, rate and storage limits, and an idempotency key with a uniqueness constraint. Sensor records remain append-only and distinct from entity/geofence activity. Do not add protocols, telemetry tables, credentials, or ingestion routes in V2.6.

## 15. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Local admin password/session is compromised | Bind loopback by default; Argon2id; session rotation/expiry/revocation; strong passphrase; TLS before non-loopback; recovery CLI. |
| Brute-force throttling locks out the sole admin | Use bounded escalating delay rather than permanent lockout; per-IP/global pre-KDF caps; documented offline CLI reset; generic responses. |
| Proxy headers poison Origin/IP/Secure decisions | Explicit public origin and trusted proxy CIDRs; proxy overwrites forwarding headers; direct app access constrained; reject unknown origin. |
| Auth middleware misses a route | One production composition wrapper and route-by-route negative tests; treat new API paths as protected by default. |
| SQLite session/audit writes increase queue contention | Keep one process/DB; batch cleanup; throttle session touches; measure lock/queue impact; avoid worker unless demonstrated. |
| Backup snapshot blocks writes or is corrupt | SQLite Online Backup API, isolated destination, checksum+integrity+foreign-key checks, size/duration benchmark, maintenance-mode fallback. |
| Restore returns stale sessions or loses later writes | Offline restore, preserve current snapshot, revoke sessions in candidate, explicit point-in-time warning, atomic same-filesystem swap and rollback procedure. |
| Event pruning breaks immutable audit semantics | Retain events indefinitely; no TTL or trigger removal; archival is copy-only in V2.6. |
| Future telemetry accidentally uses admin identity | Separate device credentials/endpoint scope and entity binding in V2.7; never share browser sessions. |

## 16. Explicit out of scope

Multi-tenancy, role matrices, SSO, OAuth/social login, public registration, email recovery, distributed identity, telemetry ingestion/storage, device protocols, background geofence jobs, automatic event pruning, database replacement/PostGIS, public deployment without a later gate, new UI redesign beyond login and CSS repair, changes to V1/V2.4 response contracts, rewriting V2.3/V2.5 event rows, running migrations/backups against the user's persistent DB during planning, and any source/dependency implementation in V2.6A.

## 17. Final recommendation

Proceed with a single-admin, same-origin cookie session; Argon2id; route-wide authorization; session-bound CSRF plus strict origins; bounded account/IP/global throttles; a separate append-only actor snapshot audit table; and an operator-only verified SQLite Online Backup/restore workflow. Retain geofence history indefinitely. Measure real database/queue cost before optimizing synchronous recalculation. V2.6A is planning complete only. The next required authorization is explicit approval to start V2.6B implementation.
