## 1. Executive summary

GeoEntity is a React 19/TypeScript and Leaflet frontend backed by a Go net/http monolith and SQLite. V2.4 adds bounded map queries, search and cursor pagination, CSV/GeoJSON exchange, and advanced entity metadata. The current boundaries support an initial geofence release without a service split or database replacement.

The recommended V2.5 scope is user-managed circle and simple polygon geofences, derived entity membership, and append-only enter/exit history. The backend owns geometry validation and membership transitions. On entity creation or coordinate-changing update, it should persist the entity, resulting membership state, and transition events atomically. The UI should visualize and manage those server-owned records, while describing transitions as events inferred from saved coordinate changes—not live tracking or delivered alerts.

Keep SQLite, the existing migration runner, and the existing entity API. Add new API routes and migration(s). Do not add telemetry, notification delivery, acknowledgement workflows, arbitrary GeoJSON types, or authentication as implicit parts of this sprint. The unauthenticated API and wildcard default bind are a critical deployment risk: the present application is suitable only for local/trusted use. External exposure must remain blocked until the security gate is delivered.

## 4. Recommended V2.5 feature contract

### 4.1 Scope and non-goals

In scope: create/read/update/delete geofence definitions; circle and simple Polygon geometry; enable/disable; current membership per entity/geofence; transitions when a saved entity position is created/changed; paginated/filterable append-only event history; map visualization and basic management UI.

Out of scope: telemetry/device ingestion, GPS polling, notification delivery, acknowledgement workflows, arbitrary GeoJSON geometry, MultiPolygon, polygon holes in the first implementation unless separately approved, geofence sharing/roles, public deployment, PostGIS, microservices, and changes to V1 entity response semantics.

### 4.2 Geometry and coordinate rules

- Entity REST coordinates continue to be named latitude and longitude in decimal degrees.
- GeoJSON positions are always [longitude, latitude]; circle center uses the same order.
- Circle radius is a positive finite number of meters. Use a documented WGS84/geodesic distance calculation; Haversine is sufficient for the initial bounded use case. Boundary points count as inside within a documented numeric tolerance.
- Initial polygon subset: one GeoJSON Polygon exterior ring, closed, with at least three distinct vertices; reject holes and MultiPolygon explicitly. Validate finite WGS84 coordinates and reject self-intersections/degenerate area. Boundary points count as inside.
- Initial implementation should reject polygons whose edges cross the antimeridian unless the chosen geometry implementation and tests demonstrate correct wrapping. Do not silently reinterpret them.
- Normalize/validate on the server. Return stable field-level errors; never persist invalid geometry. Frontend checks are convenience only.
- Geometry engine selection must be supported by golden tests, maintenance/license review and demonstrated containment behavior; a library API alone is insufficient.

**V2.5B frozen implementation details:** maximum circle radius is 10,000,000 m; the Haversine calculation uses mean Earth radius 6,371,008.8 m and includes points within 0.01 m of the radius boundary. Polygon rings are limited to 256 vertices (not counting the repeated closing position); edges are minor great-circle arcs; ring boundaries count as inside using 1e-10 radians of angular tolerance; exterior rings are normalized to counter-clockwise order; antimeridian edges and rings spanning at least 180 degrees of longitude are rejected. Polygon holes remain unsupported. These choices are implemented and covered by backend tests; revise only for a verified defect or explicit product decision.

### 4.3 Candidate additive API

The following V2.5B API shape is now implemented; membership and event routes remain proposals for V2.5C:

| Method and path | Purpose |
|---|---|
| GET /api/geofences?enabled=true-or-false&limit=&cursor= | Bounded, deterministic geofence listing; limit defaults to 50 and is capped at 100 |
| POST /api/geofences | Create validated geofence with required name, enabled, and geometry fields |
| GET /api/geofences/{id} | Read the definition |
| PUT /api/geofences/{id} | Replace the definition; membership recalculation is deferred to V2.5C |
| DELETE /api/geofences/{id} | Delete the definition; membership and event-history semantics are deferred to V2.5C |
| GET /api/geofences/{id}/events?entity_id=&from=&to=&limit=&cursor= | Bounded, stable transition history |
| GET /api/entities/{id}/geofences | Current memberships for an entity |

Implemented definition shape: {id,name,enabled,geometry:{type:Circle,center:[longitude,latitude],radius_m}} or {type:Polygon,coordinates:[ring]}. Names are trimmed, 1–100 Unicode code points, and unique after Unicode lowercase normalization. Geometry JSON is limited to 64 KiB and request bodies to 1 MiB. List cursors are opaque, keyset-ordered by created_at/id, and bound to the enabled filter. At most 100 definitions may be enabled; attempts to exceed the limit return 409 GEOFENCE_LIMIT. Errors use existing envelopes; invalid input is 400, duplicate name 409, absent ID 404, and delete success 204. Event fields/route shape remain a proposal, not implemented in V2.5B.

All new routes should use existing JSON envelope conventions and stable error codes. Bound list/event pages, body bytes, name length, ring vertices, and active geofence count. V2.5B freezes the implemented bounds at 100 active definitions and 256 exterior-ring vertices based on the pure-geometry benchmark recorded in V2.5_HANDOFF.md; this does not establish database transaction throughput. V2.5C must measure the full membership/write path before treating these as workload capacity. Use strict unknown-field behavior consistently.

### 4.4 Membership and history semantics

1. Membership is derived from persisted entity coordinates and the currently enabled geofence definition.
2. On entity creation, silently establish initial membership. On coordinate changes, calculate enabled-geofence states and emit only actual transitions. Repeated writes with identical coordinates do not emit events.
3. On geofence create/update/enable, define whether initial membership is silently established or transitions are emitted. Recommended: establish baseline membership silently on create/enable; definition edits recalculate silently, because the entity did not move. Record a separate definition activity event if auditability is required.
4. On disable, stop future evaluation and retain the last membership as inactive/unknown; do not generate synthetic exits. On delete, remove current membership but preserve historical events with ID/name snapshots.
5. For a position update, one transaction updates the entity, current membership rows, entity activity event, and zero or more geofence transition events. Any failure rolls back all of them.
6. Append-only event rows are never updated/deleted through application routes. Use stable ordering (occurred_at,id) and opaque cursors for history.
7. This event model indicates only that a saved coordinate changed from one side to another. It does not establish when the entity physically crossed a boundary or guarantee delivery latency.

### 4.5 Database evolution and migration

Use forward-only additive migrations. V2.5B sequencing was clarified by the user before implementation: migration 004 adds geofence definitions only; migration 005 adds current memberships and append-only transition events in V2.5C. Do not alter or rebuild entities unless a demonstrated need arises. Each migration must be transactional, checksum-ledgered by the existing runner, and tested on an isolated copy of a populated V2.4 database.

Proposed tables by phase:

- V2.5B / 004: geofences with ID, normalized unique name, enabled state, geometry kind and canonical JSON, timestamps.
- V2.5C / 005: entity_geofence_memberships with entity ID, geofence ID, inside state, last evaluated coordinates/time and definition version; plus geofence_events with event ID, entity/geofence identifiers, name snapshots, transition type, evaluated point, timestamp and source. Define FK deletion behavior explicitly; avoid cascading event history. Index by (geofence_id, occurred_at, id) and (entity_id, occurred_at, id).

Before migration: create and verify a backup using the approved operational process, run migration tests against copies, and verify row preservation. Never use the user's persistent database as a destructive fixture. Rollback is restore-from-backup while the service is stopped; application-level rollback is a forward corrective migration, not a down migration.

### 4.6 Frontend and state ownership

- Add geofence API/types in existing frontend/src/api and frontend/src/types boundaries.
- Add focused geofence management and event-history components rather than expanding App.tsx into geometry logic.
- Keep server definitions/membership in fetched API state. Keep drawing/edit draft geometry, map selection, visibility toggles, and unsaved validation errors ephemeral inside the map/geofence feature.
- Reuse MapView and Leaflet layers for rendering. Entity selection/CRUD and saved marker clustering must continue working. Geofence overlays must not be treated as entity markers or participate in marker clustering.
- After create/update/delete, reconcile geofence list/map overlay and event/membership queries from server responses. Avoid duplicate overlays during reloads.
- Provide loading, empty, error, validation, disabled-geofence, and deletion-confirmation states.

### Frontend and end-to-end correctness

- Verify entity selection, marker clustering, draft coordinate selection, Fit All, import refresh, and geofence overlay behavior together.

### Performance method

Do not set numeric SLOs without measurements. V2.5B measured pure geometry on an Apple M1 / darwin arm64: validating/parsing a 256-vertex polygon took 3.55 ms/op (about 63.96 KB/op, 546 allocations); evaluating 100 such polygons took 2.105 ms/op with zero allocations. These are Go microbenchmarks, not API latency or SQLite throughput. V2.5C must measure generated fixtures through the single-connection SQLite membership/write transaction, including entity count, enabled zones, vertex count, write latency, and rollback cost; V2.5D/E should measure event-list latency and frontend bundle delta. If bounded evaluation is insufficient, evaluate spatial prefilters/R-tree or PostGIS as a separate evidence-based decision; do not preemptively migrate.

## 9. Dependency recommendation

V2.5A recommendation: add no dependencies. V2.5B assessed paulmach/orb's primary README and license. The project documents 2D/planar geometry and separate geography helpers; its MIT license is compatible, but planar containment does not by itself establish the spherical edge and high-latitude semantics needed here, and the upstream issue tracker includes open point-in-polygon behavior reports. Therefore V2.5B uses a bounded pure-Go spherical implementation and adds no module dependency. References: [orb README](https://github.com/paulmach/orb/blob/master/README.md), [MIT license](https://github.com/paulmach/orb/blob/master/LICENSE.md), [point-in-polygon issue](https://github.com/paulmach/orb/issues/153), [polygon containment issue](https://github.com/paulmach/orb/issues/162). Do not add a frontend drawing library unless interactive drawing is approved and a prototype shows existing Leaflet primitives are insufficient.

## 12. Architecture overview and detailed technical audit

### Backend and data

backend/cmd/api/main.go constructs one repository, serves handler.New(store, logger), and configures request timeouts. GEOENTITY_ADDR defaults to :8080 and GEOENTITY_DB_PATH to ./data/geoentity.db. backend/internal/handler/api.go dispatches routes and stable JSON envelopes. backend/internal/entity/entity.go validates core entity fields. Repository code under backend/internal/repository owns SQL; migrations are embedded and checksum-ledgered by sqlite.go.

This is a comprehensible small monolith with explicit handler/repository/domain boundaries. Existing entity+activity and import transaction flows are a useful basis for derived spatial state. However, route dispatch is path/method branching in a large handler package, and advanced/exchange concerns share that package. V2.5 should add cohesive geofence files/interfaces without reorganizing unrelated routes. No evidence justifies a service split.

backend/internal/repository/migrations/001_create_entities.sql defines the entity table/check constraints and creation-order index. Migration 002 adds normalized metadata and activity tables; 003 adds FTS5 external-content trigram synchronization and type/status ordering indexes. Foreign keys are enabled when the repository opens; db.SetMaxOpenConns(1) serializes database use. Activity is append-only through triggers; its entity identifier has no FK so history survives entity deletion. No R-tree or other spatial index exists.

The migration runner has no down-migration mechanism. A V2.5 migration should be additive, transactionally applied with the ledger, and validated on isolated copies of a populated prior schema. Recovery after a committed migration requires a forward fix or verified backup restore while stopped. Check existing query shapes and measurements before adding indexes.

### Frontend and synchronization

frontend/src/App.tsx owns entity pages, active filters, selected entity/panel mode, mutations, marker query results, viewport and request guards. frontend/src/api/entities.ts, advanced.ts, and dataExchange.ts isolate request serialization. MapView.tsx and components/map handle viewport events, clustered saved markers, draft/user markers and ephemeral controls. EntityDetail.tsx composes overview, attributes, tags/categories, and activity. Data exchange is isolated under components/exchange.

App.tsx coordinates several server data sources and refresh effects. New geofence UI should be a focused feature with stable API types and components, not another large group of unrelated top-level state. Keep definitions/history server-owned; keep unsaved geometry drafts and overlay visibility local. Existing request guards prevent stale responses from winning but are not server consistency or snapshot mechanisms.

### API and data exchange

V1 routes remain strict and stable. Successes use a data envelope; failures use a stable error envelope. Request JSON rejects unknown properties. V2.4 adds dedicated query/map/exchange APIs rather than changing entity CRUD. Search filters are parameterized, cursor-bound, and bounded; import parser and transaction limits are explicit. A cursor is navigation metadata, not authorization. The preview SHA-256 fingerprint binds imported bytes/options but is not authorization.

### Spatial, IoT, and UX readiness

Point validation is latitude [-90,90], longitude [-180,180]. Map bounds accept west greater than east for dateline-wrapping viewports. Extent is min/max latitude/longitude, not a minimal longitude arc, so dateline-spanning data may fit a broad extent. Map queries use numeric bounds and a 5,000 response cap, not a spatial index. Current GeoJSON exchange handles entity Points; non-Point geometries are rejected.

Clustering is browser-side for persisted markers; draft and user-location layers are separate. It does not establish performance for very large data. V2.5 geometry adds correctness and scale risks; begin with a bounded supported subset and measured evaluation.

IoT readiness is structural only: entities can be typed iot_device and hold custom attributes. There is no telemetry schema/API, device identity/credentials, connectivity state, measurement history, ingestion idempotency, event-time model, threshold, alert delivery, or retention.

Search/filtering, page/load-more, map selection, import preview/validation, notifications, and loading/error/empty states exist. V2.4 handoff records browser workflows; V2.5A did not rerun browser tests. Source/component tests cannot establish Leaflet rendering, keyboard map interaction, or visual legibility. Go tests cover handlers/repositories/migrations/query/exchange; Vitest covers API/helpers/components/map state. There is no production metrics/tracing/error aggregation pipeline. The health response is static and logging is structured JSON.

## 15. Recommended V2.5 product direction

V2.5 should make saved entity positions operationally useful through geofences and explainable transition history. Address geometry correctness and event consistency first; then expose those capabilities through an accessible map and textual UI. Keep CRUD, search, clustering, import/export, metadata and current API contracts unchanged.

## 17. Database and migration strategy

Candidate migration 004 adds geofence-specific tables/indexes only; it does not change entities or migrations 001–003. Candidate tables and deletion semantics are in section 4.5. Target compatibility is populated V2.4 schema including activity, metadata, FTS triggers and entity IDs/timestamps.

Migration checks: fresh install; upgrade a populated V2.4 fixture; ledger name/checksum; foreign keys/indexes/append-only triggers; injected failure rollback; rerun; close/reopen; entity row equality. Preserve history independently from cascaded entity/geofence deletion with snapshots. For recovery use verified backup restore while backend is stopped or a corrective forward migration. No down migration is promised.

No SQL is created or executed in V2.5A. The persistent local DB has not been accessed.

## 21. Risks and mitigations

| Risk | Mitigation |
|---|---|
| False transitions from boundary, holes, high latitude or dateline | Freeze supported subset and semantics; independent golden vectors; reject unsupported cases |
| Partial entity/membership/event mutation | One transaction; injected rollback tests; identical-coordinate idempotency |
| Geometry work blocks serialized SQLite | Benchmark entity/zone/vertex counts; choose caps from evidence and reject oversized geometry early |
| History cascades away or grows indefinitely | Snapshot references, append-only triggers, explicit retention/export policy |
| Existing clients break under strict decoder | Add endpoints; preserve old DTOs/envelopes/statuses and contract tests |
| Public unauthenticated service | Keep local/trusted; security phase before external deployment or ingestion |
| Map-only controls exclude users | Text list, keyboard-accessible controls, screen-reader status and browser audit |
| Scope expands into IoT/enterprise | Keep telemetry, notifications, GIS generalization, auth and database migration out of V2.5 feature scope |

## 22. Explicit out of scope

Telemetry/sensor history/connectivity/thresholds/simulator/real-time claims; notification delivery or acknowledgement; authentication/RBAC as an implicit geofence task; external deployment; MultiPolygon/arbitrary GeoJSON import; complex GIS editing/offline tiles/prefetch; PostgreSQL/PostGIS migration; microservices; unrelated redesign; destructive DB operations; modifying migrations 001–003; touching persistent user DB; stage/commit/push/tag/release.

## 23. Final recommendation

Approve V2.5 only as a tightly scoped geofence capability: backend-defined circle/simple Polygon zones, persisted current membership, append-only coordinate-derived transitions, and focused accessible map/history UI. Implement geometry and migration correctness first, then transactional events, then frontend integration and independent verification. Keep current entity/data-operation contracts unchanged.

The V2.5B–E implementation and final verification are complete; current evidence, the deletion-review reconciliation, test results, and known limitations are recorded in `V2.5_HANDOFF.md`. The V2.5 local commit was explicitly authorized for this finalization. Do not begin V2.6 without separate authorization.
