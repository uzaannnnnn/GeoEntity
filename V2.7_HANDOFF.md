## Planning Record

This phase inspected the current repository and recorded a proposal in [V2.7_TECHNICAL_PLAN.md](V2.7_TECHNICAL_PLAN.md). Only planning documents and the roadmap were changed. No feature is implemented by this plan.

### Verified architecture constraints

- V2.6 has a single administrator, opaque hashed browser sessions, CSRF/origin enforcement, default-deny `/api` middleware, append-only administrator audit events, operator CLI support, and SQLite Online Backup/restore.
- Existing device authentication does not exist. `iot_device` is an entity type only; it is not a device identity.
- Migration ledger currently ends at 006. Future V2.7B should add migration 007, leaving migrations 001–006 and their checksums unchanged.
- SQLite is configured with one open connection. This serializes writes and means telemetry must use short transactions and bounded queries.
- V2.6 IP/global rate limiting is process-local. Its shared maintenance lock permits concurrent shared holders and does not enforce one API process. The V2.7B plan requires a separate exclusive per-database API instance lock unless it introduces a tested shared limiter.
- Entity statuses are `active`, `inactive`, and `maintenance`. Only active entities should accept telemetry. Entity deletion currently writes activity/audit snapshots transactionally; V2.7B must explicitly revoke/detach associated devices while preserving observation rows.
- The React/Vite app has an API client and component patterns, no router, and no charting dependency. A semantic table and optional small SVG are sufficient for the first dashboard.

## Design Decisions for V2.7B

- Use a separate `devices` registry, `device_credentials` records, and `device_sensors` unit registry. Device credentials are 32 random bytes; only SHA-256 hashes are stored. A credential is scoped to one device and one entity.
- Keep device provisioning, list, rotation, revocation, and detach/reassociation in the operator CLI. Show each new secret once, never accept secrets as CLI arguments, and audit lifecycle operations in the same transaction.
- Add one exact device route: `POST /api/device/v1/observations`. It accepts one observation per request; the server derives entity and device identity from the credential. All monitoring/history and device administration metadata remain administrator-session-only.
- Use strict bounded JSON, lowercase sensor IDs, a small canonical unit allowlist, finite numeric values, explicit RFC 3339 timestamps normalized to UTC, bounded metadata, and a maximum request body. The first accepted sample registers the sensor's unit; that unit is immutable for that sensor ID on the device.
- Enforce idempotency in SQLite with `UNIQUE(device_id,idempotency_key)` and a canonical payload digest. Exact retries return the original observation; a different payload with the same key conflicts.
- Migration 007 adds registry, credential, sensor unit, and append-only observation tables plus query indexes and lifecycle constraints. Observation entity IDs are snapshots without an entity FK, so entity deletion cannot cascade history. Entity deletion revokes credentials and detaches devices in its existing transaction.
- Retain telemetry indefinitely in V2.7; no automatic pruning. This keeps event history append-only but means DB and backups grow. Any later retention/archive policy needs separate authorization and evidence.
- Keep the supported deployment single-process. Initial body/rate limits in the plan are starting policy values to test and tune, not capacity claims. No new Go/npm dependencies are currently justified.
- Update V2.6 backup/restore schema-version checks for migration 007 and test both old and new backup manifests using temporary databases.

## V2.7B Implementation Record

**Status:** implementation work completed; independent V2.7C QA is the next required phase and has not started.

- Added migration 007 with `devices`, `device_credentials`, `device_sensors`, and append-only `sensor_observations`, associated query indexes, restrictive registry FKs, sensor-unit and observation-scope insert enforcement, and append-only update/delete protections. Migrations 001–006 are unchanged. No V2.7 device membership or device event tables were added; existing V2.5 geofence membership/event tables remain unchanged.
- Added the `gdev_<credential-uuid>.<base64url-secret>` lifecycle. CLI commands are `geoentity device provision <entity-id> <label> [expected-interval-seconds]`, `list`, `rotate <device-id>`, `revoke <device-id>`, `detach <device-id>`, and `reassociate <device-id> <entity-id>`. New random 32-byte secrets are displayed once; only SHA-256 hashes are stored. Device CLI operations acquire the exclusive maintenance lock. Lifecycle writes and admin audit records share a transaction.
- Added exact `POST /api/device/v1/observations` route. The payload is limited to 16 KiB, strict JSON fields, one numeric observation, canonical units and sensor IDs, explicit RFC3339 timestamp, +5 minute/90 day bounds, and bounded metadata. The transaction rechecks the exact presented credential, active device/entity scope, unit registry, and idempotency digest. Exact retries return the first record; conflicts return 409. `last_seen_at` and credential-use timestamps update at most once per minute.
- Added admin-session-protected `/api/admin/devices`, `/api/monitoring/latest`, and `/api/entities/{id}/sensors/observations` endpoints with bounded pages, sensor/time filters, and keyset history cursors bound to entity/time/sensor filters. Device list responses do not include credential IDs, hashes, or secrets.
- Entity deletion revokes credentials and detaches associated devices in the same transaction while retaining registry tombstones and observations. Inactive/maintenance entities reject ingestion without credential revocation.
- Added separate exclusive `.api.lock` to enforce one API process while retaining the shared maintenance lock. Device/global/source-IP throttles are process-local (60/device/minute, 300/source-IP/minute, 600/global/minute), bounded to 20,000 buckets with expiration. Trusted `X-Real-IP` is honored only when the direct peer matches configured trusted proxy CIDRs.
- Updated backup manifests to schema 7 and verification to accept exact schema-6 or schema-7 migration prefixes. Temporary schema-6 fixture verification/restore advances to schema 7 on application open. Rollback to a V2.6 binary after migration 007 is unsupported without restoring a pre-007 backup; after telemetry writes, retain migration 007 and roll forward.
- Added a focused React monitoring view with device status/freshness, latest readings, 24-hour default history, sensor/time filters, pagination, loading/empty/error/retry states. No package was added. Browser-driven responsive testing was not performed.

- Telemetry is retained indefinitely; the database and backups grow with every observation. No pruning or archiving exists.

## V2.7C Independent QA Result

**Verdict: FAIL.** See [V2.7C_QA_REPORT.md](V2.7C_QA_REPORT.md) for source review, complete test evidence, and findings.

- **P1 V27C-01:** Entity deletion detaches only associated devices in `active` status. A device revoked through the supported lifecycle retains its restrictive `entity_id` FK; deleting that entity fails with a foreign-key constraint error. Reproduced in an isolated in-memory SQLite fixture and confirmed against the repository deletion predicate.
- **P2 V27C-02:** `backup.Create` still declares `SchemaVersion: 6` for schema-7 DBs. Backup verification checks the internal ledger but does not compare it to the manifest version.
- **P2 V27C-03:** The sensor-filtered query-plan test uses direct `sensor_id=?`, while production uses `(?='' OR sensor_id=?)`. Independent SQLite `EXPLAIN QUERY PLAN` selects different indexes for these predicates; the current test does not verify the production plan.
- QA regression commands passed: Go tests/race/vet/build and frontend tests (29 files/172 tests)/build. `git diff --check` passed; migrations 001–006 remain byte-identical.
- Browser QA was unavailable: no browser executable, Playwright/Puppeteer package, or browser automation tool was present. No browser interactions or screenshots are claimed.
- One independent temporary 10k benchmark measured 787.9 µs/observation, 89 µs duplicate retry, 55 µs 50-row history page, 8,728,576-byte database/backup, 101 ms backup, and 372 ms restore. This is not a capacity guarantee.
- QA changed only this handoff, `V2_ROADMAP.md`, and new `V2.7C_QA_REPORT.md`. No implementation changes were made; persistent DB and `[LOCAL_PATH_REDACTED]` remained untouched; nothing was staged or committed.
