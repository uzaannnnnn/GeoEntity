## Architecture findings

- Backend is a Go monolith using `net/http`, `database/sql`, SQLite, domain validation, HTTP handlers and repository separation. Existing V1 CRUD routes use a strict JSON decoder and stable `{data:...}` / `{error:...}` envelopes.
- SQLite startup uses an embedded ordered migration runner with SHA-256 checksums and a migration ledger. Migration 001 creates the existing entity table. The repository uses one open SQLite connection and enables foreign keys.
- Frontend is React 19 + TypeScript + Vite. `App.tsx` owns entity collection/selection and CRUD flow; `EntityForm` handles base fields; `EntityDetail` renders selected entity details. V2.2 map state and controls are contained in the map feature and must remain untouched except for existing entity refresh/selection integration.
- Current frontend entity types/API client send the explicit V1 DTO. Backend rejects unknown JSON fields, so new request fields require backend support first.
- Go tests cover handler/repository/migration behavior using isolated databases. Vitest had 65 tests at V2.2 closure. No browser executable or E2E harness was available; visual browser behavior remains unverified.

## Planning decisions carried into V2.3B

- Use normalized, per-entity-type attribute definitions and typed values to support validation and future filtering; no arbitrary expressions or defaults. Preserve prior-type values across type changes.
- Keep tags as flexible labels and categories as an independent flat many-to-many taxonomy. Normalize names, enforce uniqueness, and use complete replacement for assignments.
- Add an append-only activity table without an entity FK so deletion does not erase history. Use `system` actor and nullable actor ID until authentication exists.
- Make each data mutation and its event atomic. Keep old V1 routes and request behavior; metadata uses dedicated endpoints so the strict V1 DTO remains unchanged.
- Add one numbered SQLite migration through the existing checksum-verified runner. Test only against fresh/populated temporary databases, never reset the persistent user DB.
- No new dependencies are recommended. Preserve React/TypeScript, Go, SQLite and current frontend/backend boundaries.

Exact field limits, proposed endpoint DTOs, migration tables/indexes, transaction rules, acceptance criteria, tests, risks, and frontend behavior are specified in [V2.3_IMPLEMENTATION_CONTRACT.md](V2.3_IMPLEMENTATION_CONTRACT.md).

## Known limitations and risks

- Required custom attributes cannot be enforced for V1 clients that omit metadata without breaking compatibility.
- Activity snapshots can contain sensitive values and grow over time; bound payloads and keep the app restricted to trusted/local use until authentication and retention policies are addressed.
- SQLite write concurrency remains serialized by its single connection; keep transactions short.
- Attribute values for a previous entity type need clear read-only presentation.
- Browser-level interaction and visual verification remains unavailable from the V2.2 baseline.

## V2.3B — Backend implementation and frozen API

**Status:** Backend implementation completed and verified. Frontend remains unmodified; V2.3C may begin only after the user authorizes the handoff. No commit or push was made.

### Changes

- Added immutable migration `002_advanced_entity_management.sql`; migration 001 was not edited. It creates seven approved tables: `attribute_definitions`, `entity_attribute_values`, `tags`, `entity_tags`, `categories`, `entity_categories`, and `activity_events`; it adds lookup indexes and append-only update/delete triggers for activity.
- Schema details: definitions store UUID, entity type, key, label, `string|number|boolean` type, required flag, optional number bounds/string length, archived flag, and UTC creation/update timestamps with unique `(entity_type,key)`. Attribute values store one of text/real/boolean integer per `(entity_id,definition_id)`. Tag/category catalogs store UUID, display name, unique normalized name and UTC create time; link tables use composite primary keys. Entity value/link FKs cascade; definition and catalog FKs restrict deletion. Activity stores UUID, plain entity ID, event type, fixed-width UTC nanosecond timestamp, `system` actor/null ID, payload version 1 and JSON payload capped at 65,536 bytes; entity ID has no FK.
- Existing `entities` schema and records remain unchanged. Entity metadata link tables and attribute values cascade when an entity is deleted. Catalog deletion is restricted while assigned. `activity_events.entity_id` intentionally has no FK, preserving history after entity deletion.
- V1 repository Create/Update/Delete now write their corresponding activity event in the same transaction. Definition/value operations, tag/category replacement and event write also share a transaction. A failed event insertion rolls back its source mutation. Unchanged tag/category sets do not emit duplicate events.
- Attribute storage is normalized and typed. Values are scoped to the entity's current type; a type change preserves old values and reports them under `previous_type_values`. A V1 update that omits metadata leaves them untouched.
- Activity payload size is capped at 64 KiB. To preserve V1 entity CRUD behavior for long descriptions, event summaries include at most 4 KiB of description plus `description_truncated`; string custom values in event diffs include at most 256 bytes plus a truncation marker. Persisted entity values and API responses are not truncated. Timestamps use fixed-width UTC nanosecond RFC3339 form for lexical keyset ordering; actor is `{ "kind": "system", "id": null }`. Activity payloads carry version 1 and a `changes` object containing before/after summaries or deletion snapshot.

### Frozen API contract for V2.3C

All responses use the existing `{"data":...}` envelope. Errors retain `{"error":{"code":"...","message":"...","field":"..."}}`. JSON bodies are strict, one-object JSON, max 1 MiB. Validation failures use 400; missing entity/definition/catalog IDs use 404; duplicate catalog name, invalidating definition edit, or assigned catalog deletion use 409; oversized JSON body uses 413. No database internals are returned.

| Method/path | Request | Response |
|---|---|---|
| `GET /api/attribute-definitions?entity_type=vehicle` | Supported type query required | `200 {"data":[{id,entity_type,key,label,value_type,required,min_number?,max_number?,max_length?,archived,created_at,updated_at}]}`; includes archived definitions for historical display. |
| `POST /api/attribute-definitions` | `{"entity_type":"vehicle","key":"year","label":"Year","value_type":"number","required":true,"min_number":1900,"max_number":2100}` | `201 {"data":definition}`. Max 50 active definitions/type. |
| `PUT /api/attribute-definitions/{id}` | Full mutable-field object: `{"label":"Model year","required":true,"min_number":1900,"max_number":2100,"max_length":null,"archived":false}`. Immutable key/type/entity_type are read from the stored definition and cannot be sent. | `200 {"data":definition}`. Existing values must satisfy new bounds; key/type cannot change after values exist. |
| `GET /api/entities/{id}/attributes` | UUID path | `200 {"data":{"entity_type":"vehicle","values":{"year":2025},"previous_type_values":{"vehicle.year":2025}}}`. The previous-type map contains old-type values keyed as `type.key`. |
| `PUT /api/entities/{id}/attributes` | `{"values":{"year":2025}}`; full replacement of current-type values | `200 {"data":{"values":{...}}}`. Required values enforced; omitted optional values cleared. |
| `GET /api/tags`, `GET /api/categories` | — | `200 {"data":[{"id":"uuid","name":"Fleet"}]}` |
| `POST /api/tags`, `POST /api/categories` | `{"name":"Fleet"}` | `201 {"data":{"id":"uuid","name":"Fleet"}}`; normalized duplicate is 409. |
| `DELETE /api/tags/{id}`, `DELETE /api/categories/{id}` | UUID path | `204`; assigned catalog item is 409; absent catalog ID is 404. |
| `GET /api/entities/{id}/tags`, `/categories` | UUID path | `200 {"data":[{"id":"uuid","name":"Fleet"}]}` |
| `PUT /api/entities/{id}/tags` | `{"tag_ids":["uuid"]}` | `200 {"data":[{"id":"uuid","name":"Fleet"}]}`. Complete replacement; duplicate IDs are treated as a set; max 50. |
| `PUT /api/entities/{id}/categories` | `{"category_ids":["uuid"]}` | Same item array; complete replacement; max 20. |
| `GET /api/entities/{id}/activity?limit=20&cursor=...` | Limit optional, default 20, range 1–100; opaque base64url cursor | `200 {"data":[{"id":"uuid","entity_id":"uuid","event_type":"entity.updated","occurred_at":"...Z","actor":{"kind":"system","id":null},"payload_version":1,"changes":{"before":{},"after":{}}}],"meta":{"next_cursor":"..."}}`. `next_cursor` is empty string on final page. |

Activity sorts by `occurred_at DESC, id DESC` with keyset continuation. Invalid cursor and invalid limit return 400. Activity can be read using a valid entity UUID after its entity was deleted. Existing V1 entity CRUD routes and DTOs are unchanged and continue to reject unknown fields; metadata is modified only through the dedicated endpoints above.

### Defects found and targeted corrections

1. **Stale detail requests on entity/type changes.** Async requests from a previously selected entity or entity type could resolve later and replace the current panel's state. The detail sections now remount on relevant entity identity/type, and request-generation guards discard stale load results/errors/finalizers. The definition manager also guards type switches and closing while requests are in flight. A double-trigger guard protects activity page loading. Regression tests cover the request guard; frontend tests pass.
2. **String length used JavaScript code units instead of backend UTF-8 bytes.** This disagreed with backend `max_length` validation and failed to enforce the 2048-byte default when the field was null. Validation now measures encoded UTF-8 bytes and applies the default byte limit; a multibyte regression test was added.
3. **Category assignment transaction rollback lacked a direct fault-injection regression.** Added a repository test that forces the category event insert to fail and confirms the assignment did not escape rollback. This is test-only; API semantics and schema were not changed.

No API contract, migration, backend runtime behavior, or V1/V2.2 map implementation was changed during V2.3D.

### 4. Defect Register

During live browser testing, two defects were discovered:

#### DEFECT-001 (Priority: P1 — High)
- **Title:** `MapView` `onCenterChange` Infinite Re-render Loop.
- **Subsystem:** Map Intelligence (`frontend/src/components/MapView.tsx` & `frontend/src/components/map/MapController.tsx`).
- **Symptom:** During browser execution, the browser console is spammed with >1,000–1,600 React errors:
  `Maximum update depth exceeded. This can happen when a component calls setState inside useEffect, but either doesn't specify a dependency array, or one of the dependencies changes on every render.`
  This thrashes the React rendering pipeline and degrades application responsiveness.
- **Root Cause:**
  1. In `MapView.tsx` (line 211), `onCenterChange={(lat, lng) => setCurrentCenter({ lat, lng })}` is instantiated as an unmemoized inline arrow function on every render of `MapView`.
  2. In `MapController.tsx` (lines 55–60), a `useEffect` lists `[map, onCenterChange]` as dependencies. Inside, it invokes `onCenterChange(c.lat, c.lng)`.
  3. Calling `onCenterChange` calls `setCurrentCenter` in `MapView`, which triggers a re-render of `MapView`.
  4. The re-render creates a new `onCenterChange` function reference, which triggers the `useEffect` in `MapController` again, resulting in an infinite re-render loop until React aborts.
- **Remediation Plan for V2.3F:**
  1. In `MapView.tsx`, wrap the center change handler in `useCallback` with a coordinate delta guard (e.g., only update if `Math.abs(currentCenter.lat - lat) > 1e-6 || Math.abs(currentCenter.lng - lng) > 1e-6`).
  2. In `MapController.tsx`, add a ref flag to avoid continuously firing `onCenterChange` on initial mount if the center hasn't changed.

#### DEFECT-002 (Priority: P2 — Medium)
- **Title:** Rapid Entity Selection Race / Panel Lag Under Render Pressure.
- **Subsystem:** Entity Detail Panel (`frontend/src/components/EntityDetail.tsx` & `frontend/src/App.tsx`).
- **Symptom:** When clicking rapidly between different entities in the sidebar list while background async requests or render cycles are active, the detail view can briefly exhibit selection flicker or desynchronization.
- **Root Cause:** In-flight metadata requests (attributes, tags, categories, activity) triggered during selection change can resolve in arbitrary order. While V2.3D introduced request generation guards, state transitions in `App.tsx` and `EntityDetail.tsx` could be made more atomic.
- **Remediation Plan for V2.3F:**
  1. Ensure `selectedEntity` and `sidePanelMode` state changes are batched cleanly.
  2. In `EntityDetail.tsx`, abort or ignore pending promises immediately upon receiving a new `entity.id` prop.

### QA findings and corrections

#### DEFECT-001 — P1 map center update loop

- Reproduced before the fix in Chrome: the application logged **543** `Maximum update depth exceeded` console errors during a six-second capture.

- Unit tests cover unchanged and meaningful centers, latest callback use without re-registration, and listener cleanup/remount. Browser interaction confirms genuine pan and Fit All update the coordinate inspector.
- After correction: **0** maximum-update-depth errors and **0** browser console errors in the full workflow.

#### DEFECT-002 — stale entity metadata and saves

- The existing generation guards protected reads and component cleanup, but writes could still resolve after the user switched entities. The detail shell also retained tab state across entity IDs, while delayed create/update completions could affect the current panel.
- Entity detail is keyed by entity ID, resetting entity-specific tab and child state on selection. Child metadata writes now check their request generation before changing data, loading/error state, or showing a toast. Attribute definition saves similarly ignore results after close or entity-type changes. App-level create/update panel transitions are guarded so stale completions cannot take ownership of the current selection; successful mutations still reconcile the entity list.
- Browser tests deliberately reverse A/B/C metadata response order, reject a stale request, close and reopen the same entity, delay a successful save while switching selection, and change entity type. The current entity remained correct in each case.

- The V2.3E prose reported `vehicle`, `facility`, `sensor`, and `person` as the definition selector values. That observation does not match the frozen contract or the source: supported types are `vehicle`, `iot_device`, `facility`, and `other`.
- The entity form and definition selector already use those four contract types, and the backend validation and migration agree. No API or database behavior was changed. Frontend attribute-definition validation now rejects unsupported runtime entity types as well. Backend regression tests verify all four accepted types and reject `sensor` and `person`; browser verification inspected the actual form options and definition request.
