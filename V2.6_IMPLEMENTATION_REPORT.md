The production API defaults to `127.0.0.1:8080` and refuses startup until an administrator is provisioned. Production cookie configuration requires HTTPS origin configuration; insecure development cookies require the explicit development setting and an IP loopback bind.

## D. Security Verification

- Passwords use Argon2id PHC verifiers with 16-byte salts and the planned minimum profile `m=19 MiB,t=2,p=1`; normalized password bytes use NFC. Tests cover minimum length, Unicode normalization, hash parameters, no default administrator, and credential rotation/session revocation.
- Session tokens use 32 random bytes; the database stores only SHA-256 hashes. Tests cover cookie flags, login token rotation, idle and absolute expiry, logout, and recovery revocation.
- The composed middleware defaults to denying every `/api/` route except health, login, and the session bootstrap. A composed HTTP test signs in, reads data, writes an entity with CSRF, and verifies actor attribution.
- Unsafe requests require a session-bound CSRF header and an exact configured Origin or Referer. Tests cover trusted/untrusted origin, missing CSRF, and missing origin/referer. CORS headers are not added.
- Login limits are bounded to 10 attempts/IP/minute and 120/minute global; account backoff persists and grows exponentially to a 60-second cap. Authenticated writes are limited to 60/IP/minute and 600/minute global; import/export routes use 5/IP/minute and 50/minute global. Each limiter map is capped at 4,096 buckets and fails closed for new keys at capacity. Forwarded client IP is read only from `X-Real-IP` when the direct peer is in configured trusted proxy CIDRs; spoofed forwarding headers from other peers are ignored.
- Admin audit details are bounded and redacted. Entity, metadata/catalog, import, geofence, login/logout, provision/reset, backup request, and restore events use the separate append-only audit table. Business mutation audit failures abort the same SQL transaction.

## E. Backup & Restore Verification

The backup code uses `modernc.org/sqlite` `NewBackup`/`NewRestore` through `database/sql.Conn.Raw`; it does not copy a live database file. Each snapshot is published with an atomic manifest containing UTC creation time, application/schema version, file size, and SHA-256. Backup directory/file modes are 0700/0600. Verification checks checksum/size, SQLite `integrity_check`, `foreign_key_check`, exact migration ledger checksums, and immutable audit/geofence event triggers. Retention pruning runs only after a verified snapshot is published.

Restore requires the CLI's exclusive maintenance lock. It verifies the source, stages and verifies a candidate, clears its sessions and appends a restore audit event, creates a verified online rollback snapshot of the existing database, then swaps the candidate into place. Failure tests verify that a corrupt backup is rejected before target changes and a simulated install failure restores the original database. WAL snapshot consistency was tested both with WAL active and during concurrent transactions; the test verifies an invariant across each transaction's state and event rows.

Temporary-database tests passed for driver API access, WAL backup, concurrent WAL writes, manifest permissions, checksum rejection, restore, session revocation, rollback copy retention, swap failure, and backup retention. Backup size/duration targets and RPO/RTO were not established.

## G. Known Issues and Limits

- The password blocklist is a curated in-code list, not a live breached-password service. Operators should provision a strong passphrase and V2.6C should review the policy.
- Per-IP/global throttles are in-process; a multi-process deployment needs shared limiter state or a single-process guarantee. KDF work is capped at one concurrent operation.
- Maintenance locking currently uses Unix `flock`; non-Unix targets need an equivalent implementation before they can build/run this CLI.
- Backup scheduling and off-device replication are operator-managed. Restore rollback snapshots are retained for operator validation and are not automatically pruned.
- Geofence p50/p95 samples are small and synthetic. The benchmark does not separately instrument SQLite query time, rows examined, or write-queue delay.
- V2.6C must test the production router/deployment/browser and review the code independently before any public exposure decision. This report is not a V2.6C QA or release claim.
