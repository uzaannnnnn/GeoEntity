## MVP scope

The MVP is a single-user entity management web application with a React + TypeScript + Vite frontend, a Go `net/http` REST backend, and SQLite persistence. Users can list entities, inspect details, create entities by selecting a map location or entering coordinates, edit entities, and delete entities after confirmation. Entity records are loaded from and saved to the backend; frontend-only or mock data is not the source of truth.

Required UI includes a map with OpenStreetMap attribution, markers for saved entities, an entity list/details panel, create/edit forms, and loading, empty, and error states. Leaflet and React Leaflet are the planned map libraries. No API key is required for the basic map.

Out of MVP: authentication/authorization, role management, real-time tracking, WebSockets, geofencing, route optimization, analytics, complex GIS, mobile apps, and microservices.

## Entity model

| Field | Type | Rule |
|---|---|---|
| `id` | UUID string | Required, unique, generated by the backend on create |
| `name` | string | Required; trim whitespace; non-empty after trimming |
| `type` | string | Required; one of `vehicle`, `iot_device`, `facility`, `other` |
| `description` | string | Optional; empty string is allowed |
| `status` | string | Required; one of `active`, `inactive`, `maintenance` |
| `latitude` | float64 | Required, finite, inclusive range `-90` to `90` |
| `longitude` | float64 | Required, finite, inclusive range `-180` to `180` |
| `created_at` | timestamp | Required; set by backend; UTC |
| `updated_at` | timestamp | Required; set by backend; UTC; refreshed on update |

SQLite is the persistent store. The backend is authoritative for identifiers and timestamps. Timestamps are serialized as RFC 3339 UTC strings in JSON. List ordering is not contractually significant; implementation should use a stable ordering (recommended: `created_at` ascending, then `id`).

## API contract

All endpoints are rooted at `/api`. JSON request and response bodies use `Content-Type: application/json` when a body is present. Successful entity responses use `{"data": <entity>}`; successful list responses use `{"data": [<entity>, ...]}`. Error responses use `{"error":{"code":"...","message":"...","field":"..."}}`; `field` is omitted when not applicable. Do not expose database errors, stack traces, or internal details.

| Method and path | Request | Success |
|---|---|---|
| `GET /api/health` | None | `200`, `{"data":{"status":"ok"}}` |
| `GET /api/entities` | None | `200`, `{"data":[...]}`; empty result is `[]` |
| `GET /api/entities/{id}` | UUID path parameter | `200`, `{"data": <entity>}` |
| `POST /api/entities` | Entity input without `id`, `created_at`, or `updated_at` | `201`, `{"data": <created entity>}` |
| `PUT /api/entities/{id}` | Full entity input fields except server-managed fields | `200`, `{"data": <updated entity>}` |
| `DELETE /api/entities/{id}` | UUID path parameter | `204`, empty body |

Create/update input shape:

```json
{
  "name": "Warehouse sensor",
  "type": "iot_device",
  "description": "North entrance",
  "status": "active",
  "latitude": -6.2088,
  "longitude": 106.8456
}
```

Entity output shape:

```json
{
  "id": "generated-uuid",
  "name": "Warehouse sensor",
  "type": "iot_device",
  "description": "North entrance",
  "status": "active",
  "latitude": -6.2088,
  "longitude": 106.8456,
  "created_at": "2026-11-02T00:00:00Z",
  "updated_at": "2026-11-02T00:00:00Z"
}
```

### HTTP status and error codes

| Status | Meaning | Recommended error code |
|---|---|---|
| `200` | Successful GET or PUT | — |
| `201` | Entity created | — |
| `204` | Entity deleted | — |
| `400` | Malformed JSON, invalid input, or invalid UUID | `INVALID_JSON`, `VALIDATION_ERROR`, or `INVALID_ID` |
| `404` | Valid UUID does not identify an entity | `NOT_FOUND` |
| `405` | Method not supported for the endpoint | `METHOD_NOT_ALLOWED` |
| `500` | Unexpected server failure | `INTERNAL_ERROR` |

For validation errors, provide a human-readable `message` and the relevant `field` where one field is responsible (for example, `latitude`). If a body contains multiple invalid fields, implementations may return the first error; frontend behavior must present the returned message and field. Error codes and response envelope remain consistent.

## Validation contract

### Frontend

- Trim `name` and reject it if empty.
- Require an allowed `type` and `status`.
- Require numeric, finite latitude and longitude values within inclusive bounds.
- Show understandable field-level messages and do not submit invalid forms.
- Surface backend errors without silently discarding the user's form data.

### Backend

- Validate every create and update request independently of frontend validation.
- Reject malformed JSON, missing required values, whitespace-only names, unsupported type/status values, non-finite coordinates, and out-of-range coordinates.
- Reject malformed IDs; distinguish invalid UUID (`400`) from a valid but absent entity (`404`).
- Do not write invalid data to SQLite. Generate UUID and UTC timestamps in the backend.

## Interaction rules

- On load, retrieve entities from the backend and render markers from that response.
- Selecting a marker or list item displays the entity's name, type, status, description, and coordinates.
- Add flow lets the user select coordinates from a map click and edit those coordinates in the form before submitting. After successful creation, immediately show the API response and reconcile from the entity list.
- Update flow is prefilled from the selected entity; immediately apply the successful response to details and its marker, then reconcile from the entity list.
- Delete requires confirmation; remove the entity and clear its selection immediately after successful backend deletion, then reconcile from the entity list.
- If list reconciliation fails after a successful mutation, preserve the mutation result and explain that refresh failed without describing the mutation as failed.
- When appropriate, fit the map to the available markers; use a reasonable default center for an empty dataset.
- Keep OpenStreetMap attribution visible.

## Architecture and dependencies

- Monolithic app, separated `frontend/` and `backend/` directories.
- Backend: Go standard `net/http`, `database/sql`, SQLite with `modernc.org/sqlite` (pure Go, no CGO requirement).
- Frontend: React, TypeScript, Vite, Leaflet, React Leaflet; CSS or Tailwind may be used if appropriate.
- REST + JSON. Environment variables are used for configurable settings where appropriate. Frontend API base URL and deployment routing are explicit below.
- Keep dependencies minimal and avoid features outside the MVP.

### PHASE 1 backend decisions

- SQLite uses `modernc.org/sqlite`, a pure-Go driver implementing `database/sql`. This follows the prompt's preference to avoid unnecessary native build/CGO configuration.
- `GET /api/health` returns `200` with `{"data":{"status":"ok"}}`. This finalizes the response shape that PHASE 0 left open; it does not change the endpoint or status code.
- The backend listens on `GEOENTITY_ADDR` (default `:8080`) and stores SQLite data at `GEOENTITY_DB_PATH` (default `./data/geoentity.db`).

### PHASE 3 integration decision

- In development, the frontend uses relative `/api` requests and Vite proxies `/api` to `VITE_PROXY_TARGET` (default `http://localhost:8080`). This keeps browser requests same-origin and requires no CORS headers.
- For production, the selected deployment shape is also same-origin: serve the frontend and route `/api/*` through the deployment reverse proxy to the Go backend. The Vite development proxy does not apply to the production build.
- The current deployment contract does not require separate frontend/backend origins, so the Go API does not enable CORS. If a deployment later requires cross-origin browser requests, add an explicit origin allowlist and preflight handling before deploying; do not use wildcard origins.
- `VITE_API_BASE_URL` defaults to `/api`; set it at frontend build time only if the production routing design changes.
